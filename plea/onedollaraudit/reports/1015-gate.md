## Findings

### L-1: A seller can buy PLEA with their own balance purely to shrink the computed "share sold" and manufacture fact-score points that would otherwise be out of reach

**Severity:** Low

**File:** `src/CabalGate.sol:255-264` (`_factScore`, `_factScoreAt`), `src/CabalGate.sol:422-425` (`_open`'s appeal share calc)

```solidity
function _factScore(address seller, uint256 amount, uint256 bal) internal view returns (uint8) {
    if (bal == 0) return 0;
    return _factScoreAt(seller, amount, amount * 10_000 / bal);
}
...
function _factScoreAt(address seller, uint256 amount, uint256 shareBps) internal view returns (uint8 score) {
    score = shareBps <= 2_000 ? 16 : shareBps <= 3_500 ? 9 : 3;
```

The share-of-balance band is computed from the seller's **current** balance at submit time (`plea.balanceOf(seller)`, passed in from `submitSell`/`submitFor`, line 304-305/314-328). This is explicitly by design (invariant 3: "computed at submit time"), but the band is a large, direct lever on the final score: moving from the `>35%` band (3 facts) to the `≤20%` band (16 facts) is a 13-point swing, i.e. a 13-point swing in `need` (`need = PASS_MARK − factScore`, line 427). Since `MAX_PLEA_SCORE = 45` and a plea whose computed `need` exceeds 45 is refused before payment (`CannotPass`, line 428), this lever can be the difference between a plea being **unsubmittable at all** and submittable.

**Concrete path:** A seller holding `B` PLEA who wants to sell a fixed amount `X` such that `X/B > 35%` (3 facts) can buy additional PLEA (through any router, paying the standard 2% hook fee + price impact) to grow their balance to `B' ≥ 5·X` before calling `submitSell(X, text)`. This drops `X/B'` to ≤20%, jumping from 3 to 16 facts — enough on its own to turn a `CannotPass` plea into a payable one, independent of anything the oracle panel would score. The same lever applies to the appeal path (`_open`, line 414-426) through the `oShare`/`share` minimum.

This does not violate the letter of invariant 3 (share is explicitly "of the balance... at submit time," not of some fixed historical amount), and the attacker pays real capital (the 2% swap fee plus price impact on the padding purchase) for the privilege, which bounds the griefing/abuse case to legitimate token holders willing to spend money to pass a plea. It is listed as Low rather than Medium because: (1) it costs the attacker more in absolute PLEA exposure than it saves them in oracle scrutiny in most realistic scenarios (they now hold more gated PLEA, itself subject to the same gate on a later sale), and (2) nothing is stolen from another party — it is a self-funded manipulation of one's own scoring inputs, structurally similar to the already-accepted R2-A3-2 "named-buy" dilution pattern in `FINDINGS.md`. Flagging it because the client specifically asked to look hardest at "the fact score's edges" and at anything that "lets a plea pass with a lower need" — this is a direct, reproducible way to do that which does not appear to be called out explicitly in `FINDINGS.md`.

**Recommendation:** If this lever is a concern, the fix is almost certainly a documentation/acceptance decision rather than a code change (the alternative — pinning the balance to some earlier snapshot — reopens other gaming vectors the design has deliberately avoided elsewhere, e.g. the buy-weighted hold time in `PleaHook`). No code change is suggested; flagging for the owner's explicit sign-off like the other accepted economic levers in `THREAT-MODEL.md` §3.

### I-1: `OracleAttestation`'s replay protection keys on the attester's own `requestId`, not the consumer's local request id — correctly scoped here, but worth stating explicitly as a verified invariant

**Severity:** Informational

**File:** `src/OracleAttestation.sol:173-179` (`_consume`), `src/CabalGate.sol:538` (`_consume(a.requestId)`), `src/CabalGate.sol:580-585` (`_fromIntake`)

`onOracleResult` looks up the plea via the **Intake's** `intakeId` (`_fromIntake`, keyed on `pleaOfIntake[intakeId]`), but replay-protects via `_consume(a.requestId)`, where `a.requestId` is the **oracle plane's own** request id (per `OracleAttestation.sol:25-26`'s doc comment — "not necessarily" the same value). This two-key scheme is exactly what `FINDINGS.md`'s L85-I-1 already documents and the owner has accepted (a dishonest Intake writer could *re-address* a signed score to a different pending plea, but never forge one, and never *reuse* one, because `_consume` closes on `a.requestId` and a second call with the same attestation reverts `AlreadyConsumed`).

I independently traced this to confirm the **consume key is adequate for single-use protection even though it is decoupled from `intakeId`**: a request cannot be answered twice because (a) `pleaOfIntake[intakeId]` is deleted on first success (`CabalGate.sol:547`), closing the `intakeId` side, and (b) `_consume(a.requestId)` closes the attestation side independently, so even if a dishonest writer tried to present the same signed `a` against a *second* `intakeId` mapped to a different pending plea, the second call reverts at `_consume` before any state changes land. This holds given the L85-I-1 trust assumption (the Intake only accepts `complete` from its own writer key) — no new exploit found, but it was worth independently re-deriving given how central this path is to "replay or re-address an answer," which the client asked to look hardest at. No code change needed; this is a confirmation, not a defect.

### I-2: The UTF-8 / marker text validator is internally consistent and matches the documented Unicode blocklist, but its completeness rests on an unreproduced external categorization

**Severity:** Informational

**File:** `src/CabalGate.sol:822-902` (`_validateText`, `_refused`, `_checkMarker`)

Walked the decoder (`_validateText`, lines 822-859) against the UTF-8 spec: overlong 2-/3-/4-byte sequences, the surrogate range (`cp >> 11 == 0x1b`, line 853), and the above-`U+10FFFF` ceiling are all correctly rejected; continuation-byte masking (`cb & 0xc0 != 0x80`) is correct; the `[PLEA`/`[/PLEA`/`[OBJECTION`/`[/OBJECTION` marker check (`_checkMarker`, lines 886-902) is run on every `[` in the text (not just the first) and correctly handles short-remainder inputs via its `j + 4 > n` / `j + 9 <= n` guards without reading out of bounds (calldata reads past `calldatasize` zero-pad safely in Solidity, so the unconditional `calldataload` in `_checkMarker` is sound). The `_refused(cp)` ranges (line 869-877) were spot-checked against the documented Unicode 15.1 categories (Cc/Cf/Zl/Zp/Variation_Selector/Default_Ignorable) in the doc comment above it and are consistent with the comment's enumerated ranges.

What I could **not** independently verify in this pass: whether `_refused`'s 4,240-code-point set is a byte-for-byte match against a fresh `unicodedata`-generated reference (the prior rounds' fixes, e.g. R8-A1-1, were verified that way with a Python script cross-check, which this single-pass manual review did not reproduce). Given 8 rounds of exactly this kind of fuzzing against the filter (per `FINDINGS.md` R7-A1-2, R8-A1-1), I have moderate-to-high confidence the set is complete, but flag this as an open completeness gap rather than claim a verification I didn't perform. No specific bypass was found.

## Session check (2026-10-17 09:20 UTC, against `testnet8.5` @ `af57f6d` and `next`)

- **L-1 (share band shrunk by buying more PLEA first): the mechanics hold.** `_factScore` divides by the balance at submit time. It is by design (invariant 3), and the report omits two brakes. A padding buy moves the buy-weighted hold time toward now, so up to −7 hold points for a week-old holder. Its profit effect depends on the seller: a gain gets diluted (up to +8), a loss gets smaller. And to plead X inside the 20% band the seller must hold 5X, so the net flow is a buy of up to 4X against a sale of X; the 2.5M and 50% caps still apply. The threat model's §3 does not say this outright. **Proposed: accept, and add one §3 line** (docs only, owner's OK needed).
- **I-1 (replay keyed on the plane's `requestId`): a confirmation, no defect** (same as L85-I-1, accepted).
- **I-2 (the Unicode set was not re-derived by the auditor): no defect.** Round 8 verified the 4,240 code points against Python `unicodedata` 15.1, and two tests enumerate them (`test_everyFormatCharacterIsRefused`, `test_everyDefaultIgnorableCharacterIsRefused`).

**Owner's decision (2026-10-17):** L-1 accepted, recorded as ODA-1015-1 with a THREAT-MODEL §3 line; I-1 and I-2 noted (ODA-1015-2, -3).
