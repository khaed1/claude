# Aztec Network, zk.money and launch.zk.money (status as of 3 November 2026)

Research scope: Aztec's privacy architecture and the zk.money product line (2020–2026), with emphasis on what https://launch.zk.money/ is, so a designer can compare Aztec against Tornado Cash and other Ethereum-native privacy tools. All milestones are dated; every claim carries a source URL. Where sources conflict, both are given.

## Key Question 1: What exactly is https://launch.zk.money/ (and how does it relate to https://zk.money/)?

### Takeaway
launch.zk.money is the onboarding/tag-claim entry point for the **relaunched zk.money self-custodial private stablecoin wallet** that Aztec Labs shipped on the Aztec Network L2 on 29 September 2026. It is not a token launch, airdrop portal, sequencer "Ignition" launch, or launchpad. When fetched directly on 3 Nov 2026, https://zk.money/ is a bare redirect page pointing to https://launch.zk.money, and https://launch.zk.money/ in turn 302-redirects to https://wallet.zk.money/, a JavaScript single-page app whose server-rendered HTML contains only "Loading zk.money…".

### Inferences
- launch.zk.money is best described as the "claim your tag / sign-up" front door of the relaunched wallet; the actual wallet UI lives at wallet.zk.money and is JS-rendered, so crawlers and non-browser fetchers cannot see its content.
- The Limits page's wording ("withdrawals and refunds from the previous version on Aztec v5" at $2,500, new caps $5,000/$100k) implies that by 3 Nov 2026 zk.money has already deployed a new portal on a newer Aztec version (most likely V6 "Tierra", announced by The Block the same day) and is migrating users from the V5 portal. This is inferred from the docs text, not stated explicitly.
- zk.money is architecturally a *shielded-pool wallet with a TEE co-signer and sanctions screening*, not a trustless mixer. Its trust model and caps are deliberately conservative because the underlying L2 is still "Alpha".

## Key Question 2: History — Aztec 1.0, Aztec Connect / zk.money (2021–2024), the sunset, and the pivot to the general-purpose L2 with Noir

### Takeaway
Aztec launched a confidential-asset protocol on Ethereum L1 in Feb 2020, then zk.money (Aztec 2.0 rollup, private transfers) in March 2021, then Aztec Connect (private DeFi via bridges) in July 2022; Connect was sunset starting 13 March 2023 for stated commercial/scaling reasons (not regulatory), entered withdrawal-only mode, and the operator shut down 31 March 2024. The team pivoted to Noir and a general-purpose private-smart-contract L2.

- **Aztec 1.0 on L1 (Feb 2020):** "The Aztec privacy network launched on Ethereum on Feb. 1, 2020"; only zkDai supported; used "notes" in a Bitcoin-like input/output structure; "Unlike Zcash, Aztec did not hide senders or recipients at launch"; CEO Thomas Walton-Pocock: "Our priority is to deploy PLONK to ACE in 2020" — [Cointelegraph, 3 Feb 2020](https://cointelegraph.com/news/privacy-on-ethereum-aztec-protocol-launches-on-mainnet)

### Inferences
- Aztec Connect's privacy model was already "arbitrary-value shielded notes with DeFi bridges" (not fixed denominations like Tornado Cash); the pivot kept the note/nullifier model but moved it into a general-purpose VM.
- The 2023 shutdown was a single-operator, centralized-sequencer product; its 2024 "ownership renounced, no admin keys" end-state is exactly what allowed the June 2026 drain to go unmitigated — a design lesson for any "immutable + unowned" privacy contract.

## Key Question 3: Aztec L2 architecture (private/public functions, PXE, notes/nullifiers, note discovery, accounts, fees, portals, DA, proof system, sequencers/provers, Ignition, token, mainnet timing)

### Takeaway
Aztec is a hybrid L2 where private functions are executed and proven client-side in the PXE (UTXO notes + nullifiers; Noir circuits via Barretenberg), public functions run in the AVM by permissionless sequencers, and epoch proofs (32 blocks) settle to Ethereum. The "Ignition" consensus chain went live on Ethereum mainnet 19/20 Nov 2025, the AZTEC token TGE was 12 Feb 2026, private smart-contract execution ("Alpha") launched 31 Mar/1 Apr 2026, Alpha V5 activated 21 Jul 2026, and V6 "Tierra" was announced 3 Nov 2026.

### Cited Findings

**Private vs public execution, state model**
- "A single contract can contain private functions (compiled to zk circuits) and public functions (compiled to AVM bytecode)"; "Private state uses a UTXO model, and public state uses an account-based model like Ethereum's"; Noir "compiles to ACIR, which can feed multiple proving backends"; Barretenberg is Aztec's proving backend; "PXE ... Runs private functions client-side on devices such as phones and browsers"; AVM executes public functions; sequencers "Check private execution proofs, execute public functions, update public state, propose blocks, and publish state diffs to Ethereum L1"; provers "Compute the final proof for each epoch, defined as 32 L2 blocks"; "Both roles are permissionless"; "3,500+ sequencers on the Alpha network"; privacy guarantees listed as private data, private identity, private compute — [Aztec: The Aztec Stack (26 May 2026)](https://aztec.network/blog/the-aztec-stack)
- Developers "choose which app functions are private and which are public. Private functions run and generate proofs on the user's device, while public functions run on the network" — [The Block, 3 Nov 2026](https://www.theblock.co/news/defi/2026-11-03-ethereum-l2-aztec-tierra-v6-upgrade-private-apps-432399)
- State trees: separate "public data tree" and "note hashes tree"; "Notes are encrypted UTXO-style records that only their owner can decrypt"; "The protocol stores only note commitments (hashes) in the note hash tree"; "Deleting private state means inserting a nullifier into a nullifier set. Observers can't link a note to its nullifier without the owner's keys"; "Private state is append-only"; "Reads in transactions typically consume and recreate notes, since repeated reads of the same note would link transactions"; notes created and nullified in one tx are "transient" and squashed by kernel circuits; `UintNote` supports partial notes for values set during public execution — [Aztec docs: state management](https://docs.aztec.network/developers/docs/foundational-topics/state_management)

**PXE (Private Execution Environment)**
- "The Private Execution Environment (PXE) is a client-side TypeScript library. It runs in Node.js, inside wallet software, or in a browser"; "Private inputs never leave the client-side PXE"; stores encryption keys, notes, tagging secrets; orchestrates circuit execution and proof generation; syncs state from an Aztec node; default "Kernelless mode" simulates in TypeScript before `proveTx`; keystore holds nullifier keys, incoming viewing keys, outgoing viewing keys, tagging keys; privacy caveat: "When it queries world state, such as whether a nullifier exists, the node learns what the user is looking for. Running your own node mitigates this"; no getter for registered contracts "since a dapp could probe a user's interaction history" — [Aztec docs: PXE](https://docs.aztec.network/aztec/concepts/pxe)

**Note discovery and tagging**
- Brute-force trial decryption "becomes too expensive as the network grows"; default is note tagging: every tag is `poseidon2(secret, index)` with a per-sender/per-recipient/per-contract counter; node indexes logs by tag and exposes `getPrivateLogsByTags()`; strategies: arbitrary out-of-band secret, address-derived secret (Diffie-Hellman on Grumpkin; "The recipient must register the sender's address"), non-interactive handshake (works with unknown senders but "publicly reveals that a handshake occurred"), interactive handshake (never default); decryption uses AES-128 with ECDH-derived key; PXE scans a sliding window (indices from a block ≥24h old through 20 past the finalized index), so "a sender can only emit a limited number of logs to the same recipient in the same contract within a short period"; metadata leak: "the node can observe the querying IP address and correlate it with the tags"; OMR/PIR "are currently impractical due to computational cost and are long-term goals" — [Aztec docs: note discovery](https://docs.aztec.network/developers/docs/concepts/advanced/storage/note_discovery)
- Earlier docs also say "The recipient's PXE must know the sender's address in advance to compute the shared tagging secret for that sender" — [Aztec docs via search summary](https://docs.aztec.network/developers/docs/concepts/advanced/storage/note_discovery)

**Account abstraction**
- "Aztec accounts are smart contracts"; supports "social recovery, sponsored transactions, multi-factor authentication, and granular, revocable access for compliance and selective disclosure" — [Aztec: The Aztec Stack](https://aztec.network/blog/the-aztec-stack)
- Authentication witnesses are supplied by the PXE via oracles so contracts can act on behalf of an account contract — [Aztec docs: PXE](https://docs.aztec.network/aztec/concepts/pxe)

**Fees / FPCs**
- "Fees are paid in Fee Juice, either from bridged AZTEC or through fee-paying contracts. L1 gas for bridging in and out is extra"; "public Fee Juice can reveal transaction patterns, while private Fee Juice keeps the footprint hidden" — [Baltex comparison (Oct 2026)](https://baltex.io/blog/ecosystem/aztec-vs-railgun-privacy-fees-2026-comparison)
- Aztec docs have a "Pay Fees Privately" guide covering "how private fee payment works on Aztec and includes an example using a community-built, fully private Fee Payment Contract" — [Aztec docs: FPC tag](https://docs.aztec.network/developers/tags/fpc) → [guide](https://docs.aztec.network/developers/docs/aztec-js/how_to_use_private_fee_juice)
- Search-summary findings (secondary): Fee Juice is non-transferable on L2 so FPCs are the common route; "when using Fee Juice, the fee payment is always a public transaction" (Azguard wallet help); sponsored FPCs are "useful for testing, development, and gasless transaction experiences"; the older `PrivateFeePaymentMethod` in aztec.js is deprecated in favour of a newer fully-private FPC design — [Azguard help](https://azguard-interface.pages.dev/help/transactions/network-fees); [Aztec docs: how to pay fees](https://docs.aztec.network/developers/docs/aztec-js/how_to_pay_fees); [forum: FPCs from a user POV](https://forum.aztec.network/t/understanding-fee-payment-contracts-on-aztec-from-the-pov-of-a-protocol-user/6122)
- zk.money's practical use: a sponsoring "contract on the network pays fees for you. If it runs empty, transactions stop" — [docs.zk.money Trust](https://docs.zk.money/docs/trust)

**Portals / L1 messaging**
- "Messages from Ethereum can reach Aztec in as little as 12 seconds, down from an average of two minutes" after V6 — [The Block, 3 Nov 2026](https://www.theblock.co/news/defi/2026-11-03-ethereum-l2-aztec-tierra-v6-upgrade-private-apps-432399)
- Alpha has "a Layer 1 escape hatch and no backdoor access" — [Aztec: Announcing the Alpha Network (31 Mar 2026)](https://aztec.network/blog/announcing-the-alpha-network)
- zk.money's Ethereum "portal" contract is unowned and non-upgradeable; "Every Aztec exit needs a signature from a live registered enclave" (zk.money-specific, on top of the protocol portal) — [docs.zk.money Trust](https://docs.zk.money/docs/trust)

**Proof system**
- Components named by Aztec: "the Honk proving system, the Noir zk programming language, and the Private Execution Environment (PXE), which generates client-side proofs" — [Aztec: Road to Mainnet (7 Oct 2024)](https://aztec.network/blog/road-to-mainnet)
- Barretenberg "is Aztec's proving system, one of the backends Noir can target" — [Aztec: The Aztec Stack](https://aztec.network/blog/the-aztec-stack)
- Aztec protocol spec performance targets include "Aztec Virtual Machine prover time, 10,000 step VM circuit, 15 seconds → 1.5 seconds" (targets, not measurements) — [Aztec protocol specs](https://docs.aztec.network/protocol-specs/cryptography/proving-system/performance-targets)

**Client-side proving performance (dated)**
- Alpha V5 (21 Jul 2026): native proving of a private token transfer "about 2.5 s on a consumer laptop, down from 5.2 s on V4" on an M2 MacBook (12 cores, throttled to 8); browser "about 6.8 s, down from 12.5 s"; average block time 14 s → 6 s; proving-cost parameter cut 50%; L1 verification gas down ~40%; "average fully private token transfer now costs under $0.05"; Poseidon2 ~3x faster; protocol circuit gate count ~50% lower; mobile proving not reported — [Aztec: Introducing Alpha V5](https://aztec.network/blog/introducing-alpha-v5)
- V6 "Tierra" (3 Nov 2026): "Private transaction proofs are twice as fast, taking one second to generate on a native device" — [The Block](https://www.theblock.co/news/defi/2026-11-03-ethereum-l2-aztec-tierra-v6-upgrade-private-apps-432399)
- Earlier forum data point: "Doing a AMM swap on Aztec takes about 15s on a macbook M3 and 30s on a pixel 8" (undated forum post, pre-V5 era) — [Aztec forum](https://forum.aztec.network/t/researching-aztec-applicability-for-a-privacy-first-participation-protocol/8467)
- Independent caveat: "Aztec has not published a reproducible benchmark for the proving-time or fee figures" — [Baltex (citing The Defiant)](https://baltex.io/blog/ecosystem/aztec-vs-railgun-privacy-fees-2026-comparison)

## Key Question 4: Compliance / regulatory posture ("programmable privacy", viewing keys, auditability, post-Tornado statements)

### Takeaway
Aztec's consistent line since 2023 is that compliance belongs at the application layer, enabled by per-account viewing keys and account-abstraction "selective disclosure", with no protocol-level backdoor or auditor key; the relaunched zk.money adds application-level sanctions screening of Ethereum deposit/withdrawal addresses.

### Cited Findings
- Williamson (Mar 2023): regulation sits "on the application and not the network level"; a centralized node makes network and application effectively the same; Noir/new rollup "would let developers build compliance tools into decentralized applications"; "we have not been approached by the regulators" — [CoinDesk via Yahoo](https://au.finance.yahoo.com/news/regulatory-pressure-did-not-shut-172629416.html)
- Tornado Cash context in that article: OFAC sanctioned Tornado Cash in Aug 2022; Pertsev arrested; Blender.io sanctioned; ChipMixer seized Mar 2023 — [CoinDesk via Yahoo](https://au.finance.yahoo.com/news/regulatory-pressure-did-not-shut-172629416.html)
- Williamson (2022, on Tornado sanctions): "there is a short window where heavy-handed regulation could strangle the innovation required to get us there" — [Blockworks](https://blockworks.com/news/ftx-flags-more-privacy-tools-after-tornado-cash-sanctions) (FTX blocked Aztec deposits after the sanctions — same source; [Kitco](https://www.kitco.com/news/article/2022-08-19/ftx-blocks-another-privacy-protocol-following-tornado-cash-sanctions))

- Current protocol key set: nullifier keys, incoming viewing keys, outgoing viewing keys, tagging keys per account (viewing keys are user-held) — [Aztec docs: PXE](https://docs.aztec.network/aztec/concepts/pxe); [Aztec docs: keys](https://docs.aztec.network/developers/tags/keys)
- Account abstraction enables "granular, revocable access for compliance and selective disclosure" — [Aztec: The Aztec Stack](https://aztec.network/blog/the-aztec-stack)
- Aztec Foundation blog "Who controls your privacy off-switch?" (June 2026) compares Aztec, Canton, Starknet, Tempo and zkSync and argues Aztec keeps the disclosure switch with the user rather than operators or a standing viewing key (summary from search; direct fetch returned 404) — [Aztec blog](https://aztec.network/blog/who-controls-your-privacy-off-switch)
- V6 messaging (3 Nov 2026): "No centralized sequencer and no privileged viewing keys"; Williamson: "Privacy shouldn't be something you have to request or trust someone else to protect" — [The Block](https://www.theblock.co/news/defi/2026-11-03-ethereum-l2-aztec-tierra-v6-upgrade-private-apps-432399)

- Decrypt links the relaunch to Ethereum's Hegotá upgrade privacy-pool fee proposals and Vitalik's view that special-purpose apps can reach "very strong privacy" via ZK — [Decrypt](https://decrypt.co/379621/ethereum-privacy-aztec-brings-back-zk-money)

### Inferences
- Aztec's "programmable privacy" posture is operationally: protocol = no backdoor; app/wallet = optional disclosure via user-held viewing keys plus whatever screening the app chooses. zk.money's choice to screen L1 entry/exit addresses (Chainalysis-style "visible entry and exit points") is the concrete compliance lever, and is implemented off-chain by the wallet/relayer, not enforced by the portal contract.

## Key Question 5: Known criticisms and weaknesses (proving time, note discovery/sync, anonymity set, sequencer centralization, L1 bridging linkage, UX, security)

### Takeaway
The main documented weaknesses in 2026 are: repeated critical proving-system vulnerabilities (V4 Mar 2026, V5 Jul/Aug 2026) requiring hard-fork migrations; no independent benchmarks or anonymity-set studies; metadata leakage to the node during note sync; and the public, screened L1 entry/exit points that bound the privacy of any zk.money flow. Sequencer centralization is less of a criticism now (3,000+ validators), but the 200k AZTEC stake and hardware requirements remain barriers.

### Cited Findings
- **Security track record:** critical Alpha v4 proving-system vulnerability disclosed 27 Mar 2026 (potentially enabling theft) days before Alpha launch — [KuCoin summary](https://www.kucoin.com/news/flash/aztec-network-launches-alpha-mainnet-first-ethereum-l2-with-full-privacy-smart-contracts); V4 users told to withdraw before 25 Jun 2026 — [The Defiant](https://thedefiant.io/news/defi/aztec-v4-withdraw-june-25-v5-upgrade-security-vulnerability); V5 critical soundness flaw found 27 Jul, disclosed 7 Aug 2026, exploitation status unknown; "Aztec advises treating V5 funds and apps as exposed until incident response is complete" — [Baltex](https://baltex.io/blog/ecosystem/aztec-vs-railgun-privacy-fees-2026-comparison); V6 fix required a whole-network upgrade, which is why it took ~3 months — [The Block](https://www.theblock.co/news/defi/2026-11-03-ethereum-l2-aztec-tierra-v6-upgrade-private-apps-432399); legacy Connect contracts drained ~$2.1M in June 2026 via a proof-verification flaw — [The Defiant](https://thedefiant.io/news/hacks/aztec-connect-deprecated-contract-exploit-2-1m-zk-proof)

- **Anonymity set:** "No behavioral study of Aztec's anonymity set was found ... its real-world anonymity set is unmeasured" (vs. a 2026 behavioral study of Railgun leaks) — [Baltex](https://baltex.io/blog/ecosystem/aztec-vs-railgun-privacy-fees-2026-comparison); zk.money is single-asset (DAI) with a $100k/day global deposit cap, bounding pool growth — [docs.zk.money Limits](https://docs.zk.money/docs/limits)

- **Fee-payment leakage:** "when using Fee Juice, the fee payment is always a public transaction" — [Azguard help](https://azguard-interface.pages.dev/help/transactions/network-fees); "public Fee Juice can reveal transaction patterns" — [Baltex](https://baltex.io/blog/ecosystem/aztec-vs-railgun-privacy-fees-2026-comparison)

### Inferences
- For a Tornado-style comparison: Tornado's anonymity set is per fixed-denomination pool and fully trustless; zk.money's is per-asset (DAI only), arbitrary-amount, bounded by caps, and sits behind a TEE co-signer, a hosted node (metadata), and sanctions screening — stronger on-chain unlinkability of internal transfers, weaker trust minimization and entry/exit privacy.
- The dominant 2026 risk is protocol soundness (proof-verification bugs), not deanonymization; every major release so far has shipped with or soon disclosed a critical flaw.

### Gaps
