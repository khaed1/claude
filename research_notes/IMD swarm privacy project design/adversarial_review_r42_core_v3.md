## Running findings (raw, in reading order; final ranked sections are at the end when complete)

### Batch 1 (read so far: lines 1-785; overview, pool design table, screening, token, both reviews, conventions, notes, circuit, lemmas, Pool contract tables)

**R-1. Ambiguity, dangerous reading is critical. Nothing in the circuit stops the ETH fee input (input 2) being the same note as input 0 or 1, and the two contract passages disagree on whether the contract checks it.**
- Text. `[#b-circuit]` public-input table: "nf[0], nf[1] | ... | The spent set. Both must be new and different" and "nf[2] | ... | The spent set when non-zero. Must be zero exactly when relayFee is zero". `[#b-contracts]` Pool `spend` row: "the nullifiers are unused and distinct". `[#b-circuit]`: "What the circuit leaves to the contract: ... that the nullifiers are new and distinct".
- Mechanism. With `asset = ETH`, a prover can give the same ETH note N (value v) as input 0 and as input 2. Constraints 4, 5, 6 are satisfied for both (same position, same rho), so nf[2] = nf[0]. Constraint 11 then lets the prover take v out twice: `publicAmount = v` from the asset side and `relayFee = v` from the fee side (relayer = the attacker's own address). If a builder implements the table literally (nf0 != nf1; nf2 looked up in the spent set, all lookups before any marks), nf2 == nf0 passes and every ETH note doubles per spend until `shielded[ETH]` is empty. The `spend` row says "distinct", which read as pairwise-over-three closes it; the table row for nf[2] does not say it. None of the ten lemmas covers it (it is a contract duty) and no invariant in the Pool list states it.
- Second half of the same gap. "Marks the nullifiers": if a builder marks `spent[0] = true` on the first unrelayed spend (nf[2] = 0), every later unrelayed spend fails the "unused" check. Self-sent spends are the fallback when no relayer serves, so that reading removes the fallback for good.
- Fix. In the table and the `spend` row state: "nf[0], nf[1] and, when non-zero, nf[2] are pairwise different and none is in the spent set; nf[2] = 0 is never looked up and never marked; nf[0] and nf[1] must be non-zero". Add it to the Pool invariants and to the proof list as a contract-level property ("no note position is consumed twice in one call").

**R-2. Medium. Lemma 3 ("one nullifier per note") is too weak as worded: a circuit with a free `nk` or free `rho` inside the nullifier satisfies it.**
- Text `[#b-circuit]` "What the proofs must show": "One nullifier per note. The position inside each nullifier is the position proved in the tree, so a note has exactly one nullifier and a nullifier names one position."
- The checkable part is only "the position inside the nullifier is the proved position". The "so ..." does not follow from it. A circuit whose nullifier is `H4(TAG_NF, nk', pos, rho')` with `nk'` or `rho'` a free private input (not the `nk` inside `ownerPk`, not the `rho` inside `ownerCommit`) has the right position in every nullifier and lets one note be spent any number of times with fresh `nk'`/`rho'`. That circuit also passes lemma 1 (owner derived from sk), 2, 4, 5, 6, 7, 9. Only the top statement ("every constraint above holds") excludes it, and the page's own argument for having lemmas is that the top statement alone is not trusted.
- Fix. Word lemma 3 as: "For a non-empty input, the nullifier is a function of the note's position, of the `rho` inside its `ownerCommit` and of the `nk` inside its `ownerPk`, and of nothing else. Two accepted proofs that spend the same position publish the same nullifier. A non-empty input always publishes its nullifier (nf[2] is non-zero whenever input 2 is non-empty)."

**R-3. Medium. Lemma 8 ("nothing is left free") is false for the circuit as specified, so the proof job must change the statement, and the page does not say to what.**
- Text: "Nothing is left free. Given the private inputs, every public output is determined."
- As specified: `extHash` depends on no private input (constraint 14 only makes it "take part in one constraint"); `gRef` is itself an input and is not a function of the private inputs listed; `root` is unconstrained when all three inputs are empty (constraint 5 skips the equality); `publicAsset` is unconstrained when `publicAmount = 0` (constraint 13). So four of the 13 are free in some or all cases, by design, and the contract pins them. A prover job cannot discharge the lemma as written. It will either weaken it silently or stop. The danger is the silent weakening: "determined" might be restricted to C[0..3] only, leaving nf free.
- Fix. Replace with the exact list: "nf[0..2], C[0..3], publicAmount and relayFee are functions of the private inputs and gRef. root is determined whenever at least one input is non-empty. publicAsset is determined whenever publicAmount != 0. extHash and gRef are free in the circuit and are fixed by the contract." Also state the circom-level form that tools check: every intermediate signal is determined by the input signals.

**R-4. Medium. Lemma 10 ("non-malleability") and the top statement are not properties of a constraint system, so "machine-checked against the constraint system" cannot produce them; a builder has to guess what to prove.**
- Text: "The launch gate requires the top statement and each lemma to be machine-checked against the constraint system that goes into the ceremony". Top statement: "For every proof the verifier accepts, there exist a key sk and up to three notes such that ...". Lemma 10: "Changing any one of the 13 public inputs of an accepted proof makes it rejected."
- "For every proof the verifier accepts there exist ..." is Groth16 knowledge soundness. It depends on the ceremony output and on a group-model assumption, not on the R1CS. What can be machine-checked is "every satisfying assignment of the R1CS satisfies relation R". Lemma 10 is likewise a proof-system property (and Groth16 proofs can be re-randomised by anyone: the same public inputs accept under many different proof bytes, which is harmless here only because the contract never uses the proof bytes as an identifier). The R1CS-level fact that supports it is "each of the 13 public signals occurs in a constraint that survives the compiler", and the key-level fact is "none of the 14 IC points of the final verifying key is the identity". Neither is stated.
- Also not stated: how the hash is modelled in the proofs. Lemmas 1 and 3 ("knowing nk and spk is not enough", "exactly one nullifier") hold only under collision and preimage resistance of Poseidon, which is a compression function and so is not injective. The formal statements need an explicit axiom ("no two distinct inputs with equal output are known") and the page should say so, otherwise two proof jobs will formalise different things.
- Fix. Split the list in two: (a) R1CS-level statements, machine-checked; (b) assumptions carried by Groth16, the ceremony and Poseidon, named and not machine-checked. Replace lemma 10 by the two checkable facts above plus a test on the deployed verifier that flipping each public input rejects.

**R-5. High. No lemma and no launch-gate item asks that honest spends are accepted (completeness). With immutable contracts an over-constrained circuit locks notes for good, and nothing on the page would catch it.**
- Text: all ten lemmas and the top statement are of the form "accepted implies sound". `[#b-circuit]` constraint 3: "Every value, accrued, claim, earned, publicAmount and relayFee fits in 96 bits. gRef and each input's index fit in 90 bits." Constraint 8 fixes `earned` as a quotient that must fit 96 bits.
- Why it matters here and not only in general. Several constraints reject honest states if a parameter or an implementation detail is off: (i) `earned` must fit 96 bits, i.e. `weight x value x (gRef - index) < 2^160`; whether that always holds depends on the weight scale and on g's range (checked in a later batch against the parameter table); (ii) `gRef` must fit 90 bits, so if `g` ever reaches 2^90 on-chain no proof can be made against any checkpoint and every note in every asset is frozen for ever; the Pool invariant says "g ... stays under 2^90" but not what enforces it; (iii) a builder who implements "empty" for inputs 0 and 1 slightly differently, or forgets that an all-empty spend must still pass, removes a spend type. A canary run exercises typical values, not the ends of the schedule in real time.
- Fix. Add a lemma "Completeness: for every state the Pool can reach (every note the Pool can create, any g up to the proven maximum, any checkpoint pair), the honest witness satisfies the constraint system", with the reachable ranges taken from the parameter table. Add the supporting arithmetic lemma to the contract proofs: "g < 2^90 for every reachable sequence of calls up to the end of emission", with the bound derived from the constants.

**R-6. Low. No lemma says that input 2 is an ETH note; lemma 4 names the asset of outputs only.**
- Text: "No value is created, per asset. Outputs 0 and 1 carry the inputs' asset, output 2 carries ETH, and the sums balance over the integers with the public amount and the relay fee."
- A circuit that took input 2's asset id as a free private input would turn 10^18 base units of any 18-decimal asset (one reward token, worth a fraction of a cent at the starting valuation, or one IMD) into a 1 ETH relay fee paid to the attacker's relayer address, until `shielded[ETH]` is empty. Lemma 5's "the weight of its own asset" excludes that circuit only indirectly (weights differ), and only if the formaliser reads "its own asset" for input 2 as ETH. Constraint 4 does say "the ETH id for input 2", so the top statement covers it.
- Fix. Lemma 4: "Inputs 0 and 1 and outputs 0 and 1 carry `asset`; input 2 and output 2 carry ETH; ...". Lemma 2 should also define "non-empty" in the lemma itself (value or accrued non-zero), since a circuit that tests `value == 0` alone passes the lemma as worded and admits forged `accrued`.
