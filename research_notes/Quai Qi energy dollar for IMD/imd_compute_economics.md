# IMD (IdentityMD / imd.fun) compute economics: how the swarm meters, prices and pays for agent compute (as of 13 Oct 2026)

Scope note: IMD's own surfaces are imd.fun (docs), explorer.imd.fun, api.imd.fun, the Identity-md and identity-md-launches GitHub orgs. The INFER/imdUSD whitepaper (whitepaper.imdusd.com) and imdusd.com docs are written by a third party building a stablecoin on top of IMD; its author is an IMD seat operator and measured the network from IMD's public API, so it is "independent-ish" (not the IMD team, but a stakeholder). Bankless and KuCoin are secondary coverage that mostly repeat project figures. Every number below is dated and the source given beside it. Live API readings were taken by me on 13 Oct 2026 ~09:00 UTC.

## KQ1. The IMD work pipeline: intake, assignment to seats, verification, payment, on-chain records

### Takeaway
IMD is a centrally orchestrated "control plane" (api.imd.fun) that sells six action types for a flat 0.5 IMD each (via x402/Permit2 off-chain, or on-chain through an Intake contract for oracle.request only), plans the work into jobs/nodes, offers tasks to NFT-gated "seats" that run the open-source worker on the operator's own Claude Code or Codex subscription, verifies results with a central verifier plus peer review/oracle-panel agreement, and records accepted work as reputation (ERC-8004 + a WorkRegistry, with oracle work batched into one Merkle root per UTC day). Operators are not paid per task; their only IMD income is a share of POOL4 burn trims (4.5% to seats) and launchpad allocations (10% of each launched coin split across seats).

### Cited Findings
- What IMD is: "a network to create net new 0 to 1 billion financial applications," with a consensus layer run by distributed agents; running a worker requires an IMD NFT ("seat") in a browser wallet, a paid Claude Code or Codex plan, Node 22+, Foundry v1.8.3; "running a worker does not guarantee earnings" — [imd.fun docs](https://imd.fun/docs/)
- History: Fren Pet launched on Base Aug 2023 as $FP; bridged to Ethereum Oct 2025; renamed $VIBE then $IMD May 2026 alongside a free mint of 2,000 identity.md NFTs (one per wallet); liquidity moved to Uniswap v4 and the Robinhood Chain bridge opened Sep 2026 — [imd.fun/token](https://imd.fun/token/); lead dev is Adam (@surfcoderepeat), no other team members named — [Bankless, 25 Sep 2026](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)

- Worker runtime gating: Claude Code is default when both installed; standard tasks may run on Claude Sonnet 5 at low effort or GPT-6 Luna at high effort; contract and frontend work requires an approved premium model (Claude Fable 5.1 at high effort or above, Claude Opus 5.5 at medium or above; Codex: GPT-6 Astra at xhigh or above, GPT-6.1 Sol at medium or above); a seat configured below threshold is removed from that work rather than downgraded; worker pauses 6 h after runtime sign-in/sandbox failure, 5 min on rate limit — [Identity-md/worker README](https://github.com/Identity-md/worker)
- Verification (project description via Bankless): (1) lead orchestrator agent posts work, (2) seats pick up tasks, build, submit, (3) a verifier rebuilds each submission in a sealed container to confirm only allowed files changed, (4) other seats review adversarially, (5) accepted work is logged on-chain as reputation — [Bankless, 25 Sep 2026](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)
- Verification (docs): results are checked by a verifier before going on chain under your agent; an oracle panel answer requires every member to match the quorum and a disagreeing panel produces no answer; "an accepted oracle verdict is eligibility, not a signed result" — [imd.fun docs](https://imd.fun/docs/). Website skills get worker-side build/typecheck/interaction validation; the control-plane verifier checks structure and integrity; oracle panels scan chains and "a scan that disagrees with the rest loses the seat" — [Identity-md/worker README](https://github.com/Identity-md/worker)
- On-chain records: "Oracle work is recorded once a day, not once a job": each finished job's document is hashed into its UTC day and the day's jobs form one Merkle tree over `(bytes16 jobId, bytes32 documentHash)` with one receipt carrying the root; `GET /jobs/:id/records` returns `oracleBatches` with receipt, root and proof verifiable with OpenZeppelin `MerkleProof`. Reviews are stored on the WorkRegistry and the ERC-8004 ReputationRegistry (which IMD does not deploy). Identity collection `0x0000ec93127baa929e58e97dd0095a2bfb38ec1d`, adapter `0xde152afb7db5373f34876e1499fbd893a82dd336` on chain 1 — [imd.fun docs](https://imd.fun/docs/); [api.imd.fun/health](https://api.imd.fun/health)
- Operator rewards (what is paid in IMD / launch tokens): launch swarm share = 10% of each launched token (1,000,000,000 supply, 18 decimals; 90% to requester), of which 2% is split between wallets with accepted work and 8% equally among seats connected at admission, claimed via Merkle distributor; trading fee on launch factories 1.25% per trade, 1% to the paying wallet and 0.25% to the network; earnings queryable at `GET /wallets/:address/earnings` — [imd.fun docs](https://imd.fun/docs/)
- Payment to operators for compute itself: the worker README "does not mention IMD tokens, per-task pay, or any payment terms. It says only that tasks use the operator's own agent account and quota" — [Identity-md/worker](https://github.com/Identity-md/worker); the VPS manual likewise lists no payment terms — [imd-worker-vps-manual](https://github.com/identitynode40/imd-worker-vps-manual); Bankless: "Seats don't earn much yet" — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)
- GitHub orgs: Identity-md has six public repos (research, worker, awesome-imd, identitymd-skill-crafting, univ4hook-start-template, empty-base); the worker is "generated from the main development repository" (i.e., the control plane is closed-source) — [github.com/Identity-md](https://github.com/Identity-md). identity-md-launches hosts one repo per paid launch (e.g., launch-902, launch-976, launch-1170, launch-1273), each with a PR by `surfer77` — [search results](https://github.com/identity-md-launches/launch-1170-meatbag-symbol-meat)
- Public API routes: `/health`, `/swarm`, `/skills`, `/jobs`, `/workflows`, `/oracle/requests`, `/launches`, `/seats/:tokenId`, `/publications`, `/schedules`, `/contributors`; OpenAPI at `api.imd.fun/openapi.json`; explorer `explorer.imd.fun`; 120 public reads/min/IP — [imd.fun docs](https://imd.fun/docs/)
- Chains/denomination: fees are denominated in IMD (0.5 IMD per action) while gas is paid by IMD's server wallet in ETH; Community Coins are priced on an IMD bonding curve but users trade with ETH — [imd.fun docs](https://imd.fun/docs/); [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)

### Inferences
- The network is a hub-and-spoke, trusted control plane: dispatch, verification verdicts, Merkle batching and Intake completion writes all come from IMD-operated services and a single writer key. "Decentralized" applies to the compute supply (holder-run workers), not to scheduling or verification.
- Nothing is priced per unit of compute. The only price is a flat 0.5 IMD per action regardless of how many agent-attempts it triggers; compute cost is externalized to operators' subscriptions.

### Gaps
- The control-plane source is not public, so the exact acceptance criteria, scoring ("Scores delayed" on the explorer), and how the planner chooses which seats receive offers cannot be verified.
- No documentation found of a per-task IMD payment to operators; `GET /wallets/:address/earnings` exists but I did not sample it.

## KQ2. What does a unit of work cost in real-world terms?

### Takeaway
The only measured per-unit data come from the INFER whitepaper (2 Oct 2026, from api.imd.fun/contributors over 642 seats / 644,734 attempts): an oracle node-attempt ≈114k tokens (regression; directly measured 151k on Codex, 255k on Claude), a build node-attempt ≈380k tokens, and, at OpenRouter metered rates, $0.08–0.45 per oracle attempt and ~$9.50 per workflow attempt (gpt-6-astra), $24.59 per delivered workflow. Against a $3.00 (0.5 IMD) flat fee, oracle requests at panel 5 are 7.4x over-recovered while full workflows are 3.2x under-recovered. Real cost sits in operators' $20–$200/month Claude/ChatGPT subscriptions, which the paper estimates run at 11x–164x below metered prices.

### Inferences
- Metered-equivalent cost of the network's work (my arithmetic from cited figures): tokens grew 119.2B → 198.3B between ~2 Oct and 13 Oct, ≈7.2B tokens/day; at the Claude-Sonnet-5 blend ($0.486/M) that is ≈$3.5k/day, at the Astra blend ($2.66/M) ≈$19k/day metered-equivalent, against fee income of roughly 0.5 IMD × (4,202 − 530) ≈ 1,836 IMD ≈ $15k over the same period at ~$8.5/IMD. Operators actually pay a small fraction of this through subscriptions.
- Per oracle attempt in dollars (my arithmetic): 151k tokens × $0.532/M (gpt-6-sol) ≈ $0.08; 255k × $0.486/M (Sonnet 5) ≈ $0.12; 255k × $1.756/M (Fable 5.1) ≈ $0.45. At a 1.2B-token/month Pro ceiling and 255k tokens/attempt, a $20 plan buys ≈4,700 oracle attempts/month ≈ $0.004/attempt.
- A "unit of work" exists only statistically (tokens per attempt by skill); it is not metered or priced by the protocol, and it varies ~2.5x by runtime (Codex vs Claude) and ~3x by task type (oracle vs build), and the marginal cost to operators is near zero until a subscription quota is hit, then jumps to API overage rates.

### Gaps
- OpenRouter live model pages (claude-sonnet-5, gpt-6-astra) did not render pricing via fetch; the only per-million prices available are the whitepaper's 2 Oct 2026 readings. No OpenRouter price-history series was obtained.
- OpenAI's ChatGPT pricing page returned 403; the $200 ChatGPT Pro figure is from the whitepaper only. Codex quota ceilings per tier are not documented anywhere I found.
- api.imd.fun/contributors totals (sum of attempts/accepted/rejected/tokens) could not be computed because the response is 378k chars and the fetch truncates.
- Electricity cost is unmeasured anywhere; the manual's 1 CPU / 3 GiB limits suggest it is negligible relative to inference.

## KQ3. Is there a public, manipulation-resistant metric of IMD "network work"?

### Takeaway
IMD publishes rich, free, real-time counters (agents online, seats enrolled, accepted/day, jobs done, inference tokens, per-seat attempts/accepted) via api.imd.fun/swarm, /health, /contributors and the explorer, and imdUSD's NhiFeed reads them, but every figure is self-reported by IMD's control plane, written by a single writer key on-chain, and the oracle "attestation" chain also terminates in a platform oracle signer. Nothing is costly to fake the way hashrate is; oracle work (97.6% of tokens) is unpaid and therefore has no demand-side anchor.

- Who signs oracle attestations (INFER design): the Mint Oracle role submits `oracle.request`; "the platform's oracle signer aggregates and countersigns responses as EIP-712 attestations"; INFER contracts verify that signer; a keeper relays attestations on-chain and "can withhold but cannot forge or replay"; operators with open CDPs are excluded from oracle panels; panel 50–100 agents (API cap 100), 80% quorum, toleranceBps 200, TWAP over 72 attestations; the paper elsewhere (§9.1) describes attestations as coming from "a panel of independent agents," which the summarizer flagged as a slight inconsistency — [INFER §4 L1/L3, §9.1](https://whitepaper.imdusd.com/)
- imdUSD launch parameters (imdusd.com docs, dated 4–5 Oct 2026): a signed answer must report a panel of at least 25 agents with at least 15 agreeing; "the oracle service reports these counts and signs them. - Network Health Index as implemented in imdUSD docs: the panel reads `https://api.imd.fun/swarm` and combines Participation 40% (agents online / seats enrolled, capped at 1), Service availability 30% (share of verifier, publisher, deployer up), Reliability 30% (completed / (completed + blocked + cancelled), running excluded); integer maths rounding down; `NhiFeed` stores it and the vault maps NHI ≤0.60 → mat 200% / no grace, 0.60–0.85 → mat falls to 170% and grace grows to 6 h, ≥0.85 → 170% / 6 h; "The panel measures the counters. The feed verifies the panel's signature and the fixed question, but it cannot re-fetch the counters itself"; the page "doesn't describe specific safeguards against manipulating the counters" — [imdusd.com network-health](https://imdusd.com/docs/governance/network-health)

- Reliability inputs today (my read of the swarm counters): completed 11,797 / (11,797 + 201 + 126) = 97.3%; participation 1,027/1,041 = 98.7%; all three services up → NHI ≈ 0.4×0.987 + 0.3×1 + 0.3×0.973 ≈ 0.99 — [api.imd.fun/swarm](https://api.imd.fun/swarm)
- Provider concentration / rate limiting: runtime mix 67% Codex / 33% Claude Code; 61 rate-limit events in one peak hour; INFER proposes capping any provider at 60% of oracle panel capacity and treating >3 h of prolonged rate limiting as oracle outage — [INFER §8.9](https://whitepaper.imdusd.com/)
- Independent monitoring: imtrippin/imd-monitor is an explicitly unofficial read-only dashboard whose contract-standing data comes from IMD's public standing endpoint refreshed every 30 min — [imtrippin/imd-monitor](https://github.com/imtrippin/imd-monitor); imd.fyi exists ("Understand the swarm") but renders client-side so no statistics were retrievable — [imd.fyi](https://imd.fyi/)

### Inferences
- All "work" metrics are counters maintained by IMD's closed control plane; the oracle's EIP-712 attestations are signed by IMD's oracle signer; the Intake completions are written by one IMD key. Manipulation resistance therefore rests on IMD's honesty and operational security, not on an external cost function. This is categorically different from hashrate, which is costly to fake because electricity is burned.
- The headline rate of accepted work is unstable and definition-dependent: ~29,600 accepted/24 h on 25 Sep (Bankless) and "900k monthly tasks" (~30k/day, INFER) vs 5,603 "accepted in last day" on 13 Oct (api/swarm). Either the counter semantics differ (steps vs tasks) or oracle volume was throttled by ~80% in two weeks. Both readings are IMD's own.
- The INFER whitepaper's NHI formula and the imdusd.com docs' implemented NHI differ materially (acceptance rate and 7d/30d volume vs service availability), which signals the design is still moving as of early October 2026.

### Gaps
- No independent party re-derives IMD's counters from on-chain data; the daily Merkle roots make accepted-task sets auditable but I found no third-party audit of them.
- The semantics of "accepted" (per node-attempt, per step, per job) across the swarm, explorer and contributors endpoints are undocumented; the 5.6K "steps in 24h" vs 5,603 "accepted in last day" suggests one accepted = one step.

## KQ4. Value routing: POOL4 / CappedBurnHook, sIMD staking, Community Coins, job rail; burn shares; supply

### Takeaway
IMD is a fixed-then-shrinking supply token (10M minted 2023, ~7.1M by late Sep 2026) where value is routed mainly through market mechanics, not work: the protocol-owned Uniswap v4 POOL4 trims IMD above a ratcheting cap on sells (85% burned, 6% orchestrator compute reserve, 4.5% sIMD stakers, 4.5% NFT seats), the Community Coins launchpad burns 0.5% of the IMD leg per trade, and launch factories take a 1.25% trading fee (1% to paying wallet, 0.25% network). The 0.5 IMD action fees are the only "job rail" revenue and are small; INFER's proposed 70/15/10/5 split is a design proposal, not IMD's live rule.

### Cited Findings
- Supply: 10M minted in 2023, none since, split across Ethereum, Base and Robinhood Chain, bridged 1:1, "supply only decreases"; every sell burns supply, POOL4 and Community Coin trades each burn a cut — [imd.fun/token](https://imd.fun/token/); circulating ~7.1M (≈29% burned) as of 25 Sep 2026 — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment); KuCoin repeats ~7.1M and "no new tokens can be minted"; burns are "typically executed on Base" — [KuCoin blog, 29 Sep 2026](https://www.kucoin.com/blog/imd-token-community-owned-ai-agents)
- POOL4 / CappedBurnHook: the protocol owns the main ETH/IMD Uniswap V4 pool; the hook caps how much IMD the pool holds; when sells push IMD above the cap the excess is trimmed after the swap; trimmed tokens: 85% burned, 6% orchestrator compute reserve, 4.5% stakers, 4.5% NFT seats; ETH from trims is redeployed as a buy wall below current price; the cap ratchets down ~1,000 IMD/day — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment); same split and ratchet in [KuCoin blog](https://www.kucoin.com/blog/imd-token-community-owned-ai-agents)
- sIMD staking: deposit IMD into StakedIMD vault for sIMD, an ERC-4626 share accruing IMD, no lockups or claim steps; ~2.3M IMD staked (~32% of supply) on 25 Sep; Adam renounced ownership of the staking contract on 19 Sep 2026 — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment); "Stakers receive a share of the pool's burns" — [imd.fun/token](https://imd.fun/token/)
- Community Coins launchpad: launch for the cost of gas; 1B supply each; bonding curve priced in IMD though users trade with ETH; each trade sends 1% to ETH/IMD LPs, 0.5% of the ETH side to the launcher, burns 0.5% of the IMD side; all coins share one backing pool so buying one lifts the others — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)
- Job/launch rail (IMD docs): project and hook launches mint 1,000,000,000 tokens, 10% to the swarm (2% to wallets with accepted work, 8% equally to seats connected at admission) and 90% to the requester; factory trading fee 1.25% (1% paying wallet, 0.25% network) — [imd.fun docs](https://imd.fun/docs/)
- Sources of operator income named by KuCoin: the 6% orchestrator compute reserve, the 4.5% node-operator share of POOL4 trims, and the 0.5 IMD paid-request fee; "The article doesn't give per-task payout rates for agents" — [KuCoin blog](https://www.kucoin.com/blog/imd-token-community-owned-ai-agents)
- INFER's proposed (not live) fee split for imdUSD task fees: 70% operator, 15% PSM reserve, 10% verifier pool, 5% IMD burn; at a hypothetical $10 average fee × 900k tasks, $1.35M/month to reserve; proposed tariff: oracle.request 0.10 + 0.02 per panel member (0.20/0.50/1.10/2.10 IMD at panel 5/20/50/100); contracts stage 1.0 IMD, frontend 1.0, site 0.5, revisions 0.25 each; full three-stage workflow 2.85 IMD ($17.10) — [INFER §5.1, §6.3](https://whitepaper.imdusd.com/)
- Live payment-side ETH gas: IMD's x402 gas wallet held 0.0886 ETH and the Intake writer 0.149 ETH on mainnet on 13 Oct 2026 — [api.imd.fun/health](https://api.imd.fun/health)

### Inferences
- Burn flow scales with sell volume, not with work. Staker and seat yields are therefore a function of market turnover; Bankless states this directly ("sIMD yields depend on sell flow into the POOL4 hook"). The "orchestrator compute reserve" (6% of trims) is the only mechanism where market activity funds compute, and no public figure exists for its balance or disbursements.
- Because fees are flat in IMD while costs are in dollars, a rising IMD price raises the effective price of work (0.5 IMD was $2.15 on 22 Sep, $4.87 on 25 Sep, $3.00 at the paper's $6 anchor, ~$4.2 at ~$8.5 on 13 Oct); nothing re-prices work to compute cost automatically.

### Gaps
- No contract addresses or verified source for CappedBurnHook / StakedIMD were found in fetched pages (imd.fun/token did not render them); the 85/6/4.5/4.5 split is reported by Bankless and KuCoin, not read from code.
- No cumulative figures for IMD burned via POOL4 vs Community Coins, nor the orchestrator reserve balance.

## KQ6. Proof of work / energy: where does the real cost sit and how volatile is it?

### Takeaway
IMD uses no proof of work and no energy proof; validity comes from a centralized verifier, peer review and oracle-panel agreement, and sybil-resistance comes from NFT seats (2,000, free-minted, floor ~1.99 ETH in late Sep). The "energy" burned is operators' Claude/ChatGPT subscription quota, not electricity; the real dollar cost is set by Anthropic/OpenAI list prices and plan limits, which the whitepaper calls "the least durable numbers here," and quota pressure is already visible (rate-limit events, the VPS guide downgrading from gpt-6-astra/high to gpt-5.6-luna/medium).

### Cited Findings
- No mining/PoW anywhere in IMD docs or worker README; workers need only Node 22+, a Claude Code or Codex login, and run with `CPUQuota=100%`, `MemoryMax=3G`, one concurrent task — [imd-worker-vps-manual](https://github.com/identitynode40/imd-worker-vps-manual); [Identity-md/worker](https://github.com/Identity-md/worker)
- Sybil gate is the NFT: one NFT authorizes one active device; the worker takes no work while a runtime check fails — [Identity-md/worker](https://github.com/Identity-md/worker); 2,000 NFTs free-minted May 2026 — [imd.fun/token](https://imd.fun/token/); floor 1.99 ETH, ~780 unique owners (25 Sep) — [Bankless](https://www.bankless.com/read/inside-imd-ethereum-s-new-ai-swarm-experiment)
- Cost sits in subscriptions: "Each seat uses the holder's own Codex or Claude subscription ... NFT owners, not the protocol, bear the network's compute cost" — [KuCoin News, 22 Sep](https://www.kucoin.com/news/insight/ETH/6ab2be2574fd460007c4cfa2); "Assigned work consumes the ChatGPT/Codex allowance, and always-on operation can exhaust it" — [imd-worker-vps-manual](https://github.com/identitynode40/imd-worker-vps-manual); "Tasks use the operator's own agent account and quota" — [Identity-md/worker](https://github.com/Identity-md/worker)
- Quota ceilings: Claude plans reset on rolling 5-hour windows with additional weekly limits; overage billed at API rates — [claude.com/pricing](https://claude.com/pricing); a $20 Claude Pro seat hit its session limit at 1.23B tokens/month — [INFER App. C.5](https://whitepaper.imdusd.com/); 61 rate-limit events in one peak hour across the fleet — [INFER §8.9](https://whitepaper.imdusd.com/)
- Price volatility of the substrate: "Token prices move... Model prices do not update and reflect 2 October 2026 rates"; dollar conversions are "the least durable numbers here, and the token counts the most" — [INFER App. C.6](https://whitepaper.imdusd.com/); the spread between the cheapest and dearest model blends measured on one day is 5.5x ($0.486/M Sonnet 5 vs $2.662/M Astra) — [INFER App. C.2](https://whitepaper.imdusd.com/)
- Subsidy magnitude: effective subscription rates $0.0163–$0.2334 per M tokens vs metered $0.518–$2.662 per M, i.e. 11x–164x cheaper; the paper frames the swarm as running on "the subscription substrate" — [INFER §6.5](https://whitepaper.imdusd.com/)
- Evidence of quota pressure in operator guidance: the VPS manual's "original setup used gpt-6-astra with high reasoning" but now recommends `gpt-5.6-luna` medium, with the premium tier disabled "for this trial" — [imd-worker-vps-manual](https://github.com/identitynode40/imd-worker-vps-manual)
- Unpaid oracle load dominates: oracle-assess = 88% of jobs, 97.6% of tokens, zero payers; the network "pays most for the work it throws away" (failed workflows burn 114% of completed tokens) — [INFER §6.1, §6.4](https://whitepaper.imdusd.com/)

### Inferences
- Unlike hashrate, IMD's "work" has (a) no external cost that scales with output (marginal cost ≈0 under a flat subscription), (b) a supply ceiling set by two vendors' rate limits rather than by physics, and (c) a cost basis that can be repriced overnight by Anthropic/OpenAI plan changes. Any currency anchored to IMD work would in effect be anchored to Anthropic/OpenAI consumer-plan policy.
- The IMD team's choice to route 97.6% of tokens into unpaid oracle self-assessment means the measured "work" is mostly synthetic load; a Qi-style anchor would need to separate paid, externally demanded work (~2.4% of tokens) from self-generated activity.

### Gaps
- No OpenRouter price-history series for claude-sonnet-5 / gpt-6-astra was retrievable; volatility over time is asserted (by INFER) rather than measured here.
- OpenAI ChatGPT/Codex plan prices and Codex quota windows were not retrievable (403); the $200 Pro figure is secondhand.
- No electricity measurement exists for IMD workers; given the 1 CPU / 3 GiB profile it is plausibly <$5/month per seat but this is not sourced.
