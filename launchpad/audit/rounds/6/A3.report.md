## Findings

### 1. Info: sPONDPAD gives the canonical Permit2 address a fixed, unrevocable infinite allowance (Solady default); documented for $PONDPAD (D-77) but not for the vault's shares, and PadToken turns it off

`launchpad/contracts/src/StakedPONDPAD.sol:37`

```
contract StakedPONDPAD is ERC4626, FixedOwnable {
```

Judge's verdict on the audit_economics finding: reproduced, kept as Info, scope corrected. Solady v0.1.9 (lib/solady, the ERC20 base of StakedPONDPAD through ERC4626 and of PondPadToken) returns true from `_givePermit2InfiniteAllowance()`, so `allowance(holder, 0x000000000022D473030F116dDEE9F6B43aC78BA3)` is always `type(uint256).max`, `approve(PERMIT2, x)` for any x other than max reverts `Permit2AllowanceIsFixedAtInfinity()`, and a `transferFrom` sent by that address skips the allowance check. `upstream/make_staking.py` doesn't add an override to the generated vault, while `PadToken` (the coin token) overrides it to false. Correction to the specialist: DECISIONS D-77 already records that `PondPadToken` keeps the default and that `PadToken` turns it off, so the $PONDPAD half is documented; the sPONDPAD half is not (THREAT-MODEL invariant 13 / ARCHITECTURE §5.3 describe sPONDPAD as plain ERC-4626 shares). This is POOL4's StakedIMD behaviour unchanged (THREAT-MODEL §3: report only if it breaks an invariant; it doesn't: Permit2 is immutable and only moves tokens on the holder's own Permit2 signature or approval, and the one-block hold still applies through `_beforeTokenTransfer`). It is kept because it is undocumented for the staked position and inconsistent with the project's own PadToken: a Permit2 signature phishing reaches staked positions as well. THREAT-MODEL invariants checked for this area by the judge: 13 (no rescue of stake, shares or buffer; pause bounds; powers expire), 14 (own asset count, reward gate, 1/7 per drip, hold, PadBuyer's sink and bound), 15 (splitter sums and ranges, WorkerFund and GrowthFund sinks and caps), 20 (airdrop leaf format, voucher binding, 100 distinct listed wallets, delegation nonces, vesting and sweep timing), 21 (team vesting schedule), and the fee-routing part of 11 through `MarketController.collectFees`. No path breaking any of them was found. Fix (docs or code, the owner's choice): add `function _givePermit2InfiniteAllowance() internal pure override returns (bool) { return false; }` to `StakedPONDPAD` through `make_staking.py` (the site approves Permit2 explicitly for market trades, D-77, and sPONDPAD isn't traded through the router), or document the standing allowance in THREAT-MODEL §3 / ARCHITECTURE §5.3 next to D-77's note on $PONDPAD.

**Reproduction**

test/scratch/A3Probe.t.sol `test_probe_permit2FixedInfiniteAllowance` (passes on this tree, i.e. the behaviour is present): deploy PondPadToken and StakedPONDPAD; holder deposits 10e18. Expected for plain ERC-20 / ERC-4626 shares: `allowance(holder, PERMIT2)` is 0 on both and `approve(PERMIT2, 0)` succeeds. Actual: both allowances read `type(uint256).max`, both `approve(PERMIT2, 0)` calls revert `Permit2AllowanceIsFixedAtInfinity()`, and in the next block `vm.prank(PERMIT2); vault.transferFrom(holder, attacker, shares)` succeeds with no approval ever given. `grep -rn _givePermit2InfiniteAllowance src/` finds only PadToken.sol:213.

### 2. Info: PadBuyer.buy() rolls back its own forward() when it reverts, and the keeper never calls forward(), so the stakers' $PONDPAD fee share waits in PadBuyer until enough IMD arrives for a buy

`launchpad/contracts/src/PadBuyer.sol:78`

```
        forward();
        if (block.timestamp < lastBuyAt + interval) revert TooSoon();
```

Judge's verdict on the audit_permissions finding: reproduced, kept as Info (liveness only). `buy()` calls `forward()` first and then reverts `TooSoon` (inside the 10-minute interval) or `NothingToBuy` (less than `minChunk` = 1 IMD held), which undoes the forward. `keeper/keeper.mjs` line 134 only sends `PadBuyer.buy`, and only when the buyer holds at least 1 IMD and its interval has passed; it never sends `PadBuyer.forward`. At the mainnet defaults the buyer spends up to 25 IMD every 10 minutes, so it sits near zero IMD most of the time: the $PONDPAD that `FeeSplitter.distributeToken` sends it (the stakers' 40% of the market's sell-side fees, D-38) stays parked until a later IMD inflow of at least 1 IMD lets a `buy()` succeed. No funds are at risk, `forward()` is permissionless and anyone can call it, and THREAT-MODEL invariant 14 (PadBuyer can send $PONDPAD nowhere but the dripper) holds. Fix: in the keeper, send `PadBuyer.forward()` whenever `pondpad.balanceOf(padBuyer) > 0`, independently of the IMD check; or make `buy()` return after the forward instead of reverting when there is nothing to buy (the keeper simulates before sending, so it would then need a view such as `canBuy()` to gate on).

**Reproduction**

test/scratch/A3Probe.t.sol `test_probe_forwardRolledBackWhenBuyReverts` (passes on this tree): deploy PadBuyer with a zero IMD balance and send it 50e18 $PONDPAD. `buyer.buy()` reverts `NothingToBuy()`; expected per the NatSpec ('Forwards any $PONDPAD held to the dripper, then buys'): the $PONDPAD reached the dripper; actual: `pondpad.balanceOf(buyer) == 50e18` and the dripper's balance is unchanged. A direct `buyer.forward()` then moves the 50e18 to the dripper. The same happens with `TooSoon` inside the interval. `grep -n forward launchpad/keeper/keeper.mjs` finds nothing.

### 3. Info: StakedPONDPAD.maxDeposit / maxMint report no limit for the two receivers deposit and mint always refuse (ERC-4626 max-view deviation)

`launchpad/contracts/src/StakedPONDPAD.sol:264`

```
        return paused() ? 0 : super.maxDeposit(to);
```

Judge's verdict on the first audit_flow finding: reproduced, kept as Info. Since R4-A3-1, `_deposit` reverts `InvalidReceiver` when `to` is address(0) or the vault itself, but `maxDeposit(to)` and `maxMint(to)` still return `type(uint256).max` for those receivers. ERC-4626 requires the max views to return the largest amount that would not revert for that receiver, and the vault's own pause-aware overrides follow that rule for the paused case. An integrator that previews with `maxDeposit` gets a non-zero limit and then a revert. No funds are at risk and nothing in PondPad relies on these views; same class as R3-A3-4 / R3-A3-6. Fix: in `maxDeposit` / `maxMint` return 0 when `to == address(0) || to == address(this)`, added through `upstream/make_staking.py`.

**Reproduction**

test/scratch/A3Probe.t.sol `test_probe_maxViewsForRefusedReceivers` (passes on this tree, i.e. the deviation is present): `vault.maxDeposit(address(0))` returns `type(uint256).max` and `vault.maxMint(address(vault))` returns `type(uint256).max`; then `vault.deposit(1e18, address(0))` and `vault.mint(1e24, address(vault))` both revert `InvalidReceiver()`. Expected per ERC-4626: both views return 0 for those receivers.

### 4. Info: GrowthFund.grant and payJob accept amount 0 for any token, uncapped ones included, and still call the token and emit Granted / JobPaid

`launchpad/contracts/src/GrowthFund.sol:110`

```
        if (spent > grantCap[token]) revert AboveCap();
```

Judge's verdict on the audit_math finding: reproduced, kept as Info, one detail corrected. The per-epoch cap check is `spent > grantCap[token]`, so a grant of 0 passes for a token whose cap is 0 (an uncapped token): the fund then calls `transfer(to, 0)` on that arbitrary `token` contract from the GrowthFund address and emits `Granted`. `payJob` has the same boundary with amount 0 (`relaySpent + 0 > relayCap` is false even at the cap). Correction: Solady's `safeTransfer` reverts `TransferFailed` for an address without code (it checks `extcodesize` when the return data is empty), so the call only goes through to a contract; the specialist's reproduction used a contract, which is right. No funds move, GrowthFund holds no privilege elsewhere that the outgoing call could use, and the callers are the granter (team Safe) and the relay, so this is a boundary gap in the 'only capped tokens' rule of THREAT-MODEL invariant 15 and a misleading event, not a loss. Fix: refuse `amount == 0` in `grant` and `payJob` (or require `grantCap[token] != 0` in `grant`).

**Reproduction**

test/scratch/A3Probe.t.sol `test_probe_growthFundZeroGrantOnUncappedToken` (passes on this tree): GrowthFund deployed with caps for IMD and $PONDPAD only; as the granter call `grant(address(recordingToken), to, 0, ref, reason)` where `grantCap[recordingToken] == 0`. Expected: revert (uncapped token). Actual: the call succeeds, the mock records one `transfer` call with `msg.sender == address(fund)`, and `Granted(epoch, token, to, 0, ...)` is emitted; a 1-wei grant of the same token reverts `AboveCap()` as intended; `payJob(0, ...)` by the relay succeeds.

### 5. Info: Undocumented sink: $PONDPAD sent straight to TeamVesting after deploy joins the team's schedule and is paid to the beneficiary

`launchpad/contracts/src/TeamVesting.sol:44`

```
        uint256 total = token.balanceOf(address(this)) + released;
```

Judge's verdict on the second audit_flow finding: reproduced, kept as Info (docs). `vestedAmount` defines the allocation as the contract's live balance plus what it released, so any $PONDPAD that reaches the vesting contract after deploy (a mistaken transfer, a grant, a sink pointed at it) becomes part of the 20M schedule and vests to the beneficiary (the team Safe) on the same clock; after day 180 it is releasable at once. THREAT-MODEL §3 lists the other addresses that act as sinks (PadHook, PadMarketHook, BondingCurve, a coin's own address, the vault through `syncRewards`) but not TeamVesting, nor AirdropDistributor (anything sent there is swept in full to the dripper after the claim window). Only the sender's own funds are affected and invariant 21 (always to the beneficiary) holds. Same class as R4-A1-4 / R3-A2-4. Fix: documentation only (THREAT-MODEL §3, TeamVesting NatSpec).

**Reproduction**

test/scratch/A3Probe.t.sol `test_probe_teamVestingLateFunding` (passes on this tree): fund TeamVesting with 20M, set the market clock, warp 200 days, `release()` pays the Safe 20M; then transfer 1e18 to the vesting contract from any wallet: `releasable()` returns 1e18 and `release()` pays the Safe 20M + 1e18. Expected (docs): THREAT-MODEL §3 names TeamVesting and AirdropDistributor as sinks.
