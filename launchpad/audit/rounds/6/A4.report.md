## Findings

### 1. Low: CreatorVault: the R5-A1-1 'no other coin as recipient' guard is a time-of-set check, so a coin's recipient can become another registered coin by naming its predicted CREATE2 address before it launches

`launchpad/contracts/src/CreatorVault.sol:132`

```
                || (recipient != coin && recipientOf[recipient] != address(0))
```

Merged from the permissions and flow specialists (same mechanism, same fix). `_checkRecipient` (used by `register` at launch and by `setRecipient`) refuses another registered coin by reading `recipientOf[recipient]` at the moment the recipient is set; nothing re-checks when a coin is registered later or when `claim` pays. `PadFactory.predictAddress` makes every future coin address public (CREATE2 over creator and salt; the suite itself uses it to route fees to a coin's own holders at launch), and `recipientOf` of a not-yet-launched coin is zero, so a creator can launch coin A with `feeRecipient` = the predicted address of coin B (or call `setRecipient(A, predictedB)`), then launch B. A's recipient is then a registered PadToken for good, exactly the state the R5-A1-1 fix (d65698e) says is unreachable (CreatorVault NatSpec, THREAT-MODEL section 3, FINDINGS R5-A1-1). Consequences: (1) a PadToken never calls `setRecipient`, so nobody can ever change A's recipient again; (2) anyone's permissionless `claim(A)` transfers A's accrued creator fees to B's address, where `PadToken.distribute()` (public, and run by every B trade with a holder tax) credits them to B's current holders as an instant lump, not through the 7-day holder stream, since `to != coin`; (3) `SwarmBudget.requestSpend(A)` needs `msg.sender == B` (a contract that never calls), `sweepToHolders(A)` needs `recipientOf(A) == A`, and `cancel` has nothing to cancel, so A's swarm-budget share of every trade is locked for ever. Only A's own recipient can create the state (THREAT-MODEL section 3 counts any other address as the recipient's choice) and only A's creator fees and swarm budget are affected, so Low, the same class and harm as R5-A1-1; but the documented rule does not hold over time and the fix's regression test (`test_vault_refusesRecipientsThatStrandFees`) covers coins that already exist only. Invariants checked: 6 (lumps to holders go through the stream; here the lump is A's recipient's own gift to B, so no invariant breaks), 17 (only the recipient changes a recipient), section 3's recipient rule. Fix options (any one makes the proof pass): (a) re-check in `claim`: if `to != coin && recipientOf[to] != address(0)` revert `InvalidRecipient` (the recipient can still move on with `setRecipient`, and a PadToken recipient can never be moved, so pair it with (b)); (b) keep a reverse index (`isRecipient[address]` count maintained by `register` / `setRecipient`) and have `register` refuse a coin whose address is already some coin's recipient, so B's launch at the predicted address reverts; (c) document the gap in THREAT-MODEL section 3 and the R5-A1-1 row.

**Reproduction**

Base harness (fresh deployment, test contract is owner). 1) `predictedB = factory.predictAddress(paramsB, creator)` for a coin B not yet launched (`predictedB.code.length == 0`). 2) creator calls `router.launchWith(paramsA with feeRecipient = predictedB, imd, 1e18, false, 0, 0, address(0))` with fees (100, 0, 0, 10_000): succeeds, `vault.recipientOf(A) == predictedB` (no code, no registration, so `_checkRecipient` passes). The same state is reached by `vault.setRecipient(A, predictedB)` from A's recipient (judge probe `test_probe_setRecipientToPredictedAddress`). 3) creator launches B with paramsB: `B == predictedB`, `vault.recipientOf(B) == creator`, so `recipientOf(A)` is now a registered coin other than A. Control: `vault.setRecipient(B, A)` by B's recipient reverts `InvalidRecipient`, showing the state is one the fix means to refuse. 4) alice buys 100 IMD of A: `vault.balanceOf(A) == 0.5e18`, `budget.available(A) > 0`. 5) anyone calls `vault.claim(A)`. Expected (per R5-A1-1 and THREAT-MODEL section 3): A's fees never reach another coin. Actual: `imd.balanceOf(B) == 0.5e18`; after bob buys B, `PadToken(B).distribute()` credits it to B's holders at once. 6) `vault.setRecipient(A, creator)` by creator reverts `Unauthorized`; `budget.requestSpend(A, 1, 0)` by creator reverts `Unauthorized`; `budget.sweepToHolders(A)` reverts `Unauthorized`: A's recipient can never be changed and its swarm budget is locked. Run: `forge test --match-path test/scratch/CreatorVaultLaterCoinRecipient.t.sol` fails on this commit with "A's creator fees must not land on coin B: 500000000000000000 != 0" (the flow specialist's proof, re-run by the judge).

### 2. Low: PadConfig: the guardian can resume launches, not only pause them, so an owner (48 h timelock) pause and the deploy-run pause are undoable instantly by the guardian

`launchpad/contracts/src/PadConfig.sol:170`

```
        if (msg.sender != guardian && msg.sender != owner()) revert NotGuardian();
```

THREAT-MODEL section 1 lists the Safe's guardian power as 'pause new launches'; ARCHITECTURE section 5.6 ('Guardian (instant): pause NEW launches only', 'may pause new launches instantly') and PadConfig's own NatSpec ('A guardian may pause new launches instantly, nothing else') say the same. The code gives the guardian the whole setter, so it can also set `launchesPaused = false`. Two concrete effects: (1) a pause decided through the 48 h timelock (the owner) can be undone by the guardian at once, so the timelocked path does not bind for this setting; (2) during the deploy run the script pauses launches at step 3 (Deploy.s.sol line 344) so no fee is split while the splitter's stakers recipient is still the Safe placeholder (the R3-A4-12 fix), and the guardian is already the Safe from the PadConfig constructor (line 338), so the Safe could unpause between the run's transactions and a launch plus trades in that window would pay the stakers' 40% of protocol fees to the Safe instead of PadBuyer. Low: the guardian is the Safe, which is also the only proposer to the timelock, so there is no second party to defeat and the deploy window is minutes; but it is a documented bound (THREAT-MODEL section 1: 'powers must stay inside the bounds in code') the code does not enforce. Fix: split the setter (`pauseLaunches()` for guardian or owner, `setLaunchesPaused(bool)` owner only) or keep one setter and require `msg.sender == owner() || (msg.sender == guardian && paused)`; update `test_governance_strangersOnOwnerSetters` or add the proof test. Invariants checked: 22 (launches paused until fee routing is final) and the section 1 guardian row.

**Reproduction**

Standalone (proof test): `new PadConfig(owner, imd, splitter, growth, guardian, settings)`. `vm.prank(guardian); config.setLaunchesPaused(true)` succeeds (documented). `vm.prank(guardian); config.setLaunchesPaused(false)`: expected revert (the guardian may only pause); actual: succeeds, `launchesPaused() == false`. Run: `forge test --match-path test/scratch/GuardianCanOnlyPause.t.sol` fails on this commit with "next call did not revert as expected".

### 3. Info: SwarmBudget.setRelay and its constructor accept address(0) (PadConfig.setGuardian too), unlike the sibling setters hardened in round 5 (R5-A4-5 / R5-A4-6 class)

`launchpad/contracts/src/SwarmBudget.sol:129`

```
        relay = relay_;
```

Merged from the flow and economics specialists (same setter, same fix). `SocialRegistry.setVerifier` (R5-A4-6), `VersionRegistry.setVerifier` (R5-A4-5), `AirdropDistributor.setVerifier` and `WorkerFund.setWorkerRewards` refuse an unusable address; `SwarmBudget.setRelay` (48 h timelock) and the constructor's `relay_` store any value, address(0) included. With `relay == address(0)` no account can call `release` and `cancel` loses its relay path, so every reserved request of every coin waits on the requester's own cancel or on another 48 h change (a release to address(0) would also be refused by the OFT's transfer). Fix: `if (relay_ == address(0)) revert ZeroAddress();` in `setRelay` and the constructor (and the same in `setGuardian`, or document that the guardian may be unset). `GrowthFund.setRelay` has the same pattern, outside this area.
