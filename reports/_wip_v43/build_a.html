Build specification

This section is what a build job works from. It replaces the design table of the first version 4 wherever the two differ. Three reviews explain how it got here: the review of the new parts, the independent review of revision 4.1 and the review of revision 4.2. Values marked param come from the parameter table and are frozen before the trusted-setup ceremony. Names are working names. Where this section does not say what to do, a builder stops and asks.

Conventions

ItemDefinition
FieldThe BN254 scalar field. Every hashed value is less than its modulus p, and the contracts reject inputs that are not
HashPoseidon with circomlib's parameters. H2, H3 and H4 take two, three and four inputs. On-chain they are the three poseidon-solidity contracts already on mainnet, at 0x3333333C0A88F9BE4fd23ed0536F9B6c427e3B93, 0x4443338EF595F44e0121df4C21102677B142ECF0 and 0x555333f3f677Ca3930Bf7c56ffc75144c51D9767. The pool pins each by code hash, calls it with staticcall, and the build checks each against the circuit with shared test vectors
Domain tagsEvery hash that is not a tree node or a leaf bundle takes a tag as its first input: TAG_SPK = 1, TAG_NK = 2, TAG_PK = 3, TAG_OC = 4, TAG_NF = 5. A note's packed word carries TAG_NOTE = 6 above bit 200, so it can never equal a small tag
AmountsUnsigned, at most 96 bits, in the asset's base units. The token's supply times 1018 must stay under 296, which allows up to about 79 billion tokens. A deposit of the token is limited to 296 − 1 like any other value
Asset id8 bits. 1 is ETH, 2 USDT, 3 USDC, 4 IMD, 5 the pool's own token. Zero means "no asset". The list is a constant table in the circuit and the pool
WeightsOne integer per asset per base unit, in the same table. IMD has 18 decimals and weight 1. ETH's weight is the number of IMD one ETH buys on the day the parameters are frozen, rounded, about 807 today. USDT and USDC have 6 decimals and weight ETH's weight × 1012 ÷ ETH's dollar price, rounded, about 3.79 × 1011 today. The token's weight is 0 param
Reward indexOne number g for the whole pool, fixed-point with 64 fractional bits. It only grows. With the weights above and a supply of one billion it cannot pass 275 on mainnet or 281 on the canary. The build script computes the largest possible value from the parameter file and fails unless it is under 288. If g would still pass 290 − 1 the pool holds it there and emission stops
TreeAppend-only, depth 32, nodes H2(left, right). The empty leaf is ZERO = keccak256("murmuration.zero") mod p and empty subtrees are built from it. One leaf per transaction: leaf = H4(C0, C1, C2, C3), a bundle of four note commitments. An unused slot in a bundle holds the field element 0, which is no note's commitment
Positionpos = 4 × leafIndex + slot, where slot is 0 to 3. It identifies one note for good
TimeSeconds of block time, never block counts. Two fixed points. GENESIS is a timestamp in the final build param: nothing can be launched before it, and screening epochs of one day are counted from it. START is the time the registry first applies a batch, recorded once: caps, emissions and the deposit window count from it, so a slow start costs nobody anything. Before START the caps are those of the first step, nothing is emitted and deposits are open. A reward checkpoint window is one hour and a cap step is 90 days, both counted from START
Token transfersThrough a wrapper that accepts tokens returning no value, as USDT does, and that fails when the target has no code. A token transfer that fails reverts the call
ETH paymentsBy call with a gas allowance of 50,000 param. If the call fails the amount is credited to owed[address] and the transaction goes on. Anyone can later call claimOwed(address), which sends the credit to that address and nowhere else. The one exception is a refund, which reverts if its payment fails

Keys, notes and addresses

// Keys. sk never leaves the wallet.
spk      = H2(TAG_SPK, sk)                 // proves the right to spend
nk       = H2(TAG_NK,  sk)                 // computes nullifiers
ownerPk  = H4(TAG_PK, spk, nk, d)          // d: a diversifier, so that a wallet's notes cannot be linked to each other on-chain

// A note is (asset, value, accrued, index, ownerPk, rho).
ownerCommit = H3(TAG_OC, ownerPk, rho)     // hides the owner; this is all a deposit reveals about its recipient
packed      = TAG_NOTE·2^200 + accrued·2^104 + value·2^8 + asset
commitment  = H3(packed, index, ownerCommit)
nullifier   = H4(TAG_NF, nk, pos, rho)     // one per note position; published when the note is spent

// Everything else comes from a 32-byte seed. HKDF is HKDF-SHA256 with an empty salt; the quoted label and what follows it are the info string.
spendRoot = HKDF(seed, "murmuration/v1/spend", 64 bytes)          sk = spendRoot mod p
viewRoot  = HKDF(seed, "murmuration/v1/view", 32 bytes)
xwingKey  = the X-Wing key pair generated from HKDF(viewRoot, "xwing", 32 bytes)
// Deposit number n, a per-wallet counter from 0:
rho = first 31 bytes of HKDF(viewRoot, "deposit-rho" ‖ n)         d = first 8 bytes of HKDF(viewRoot, "deposit-d" ‖ n)
// Outputs 1, 2 and 3 of a spend whose first nullifier is nf0:
rho = first 31 bytes of HKDF(viewRoot, "out-rho" ‖ nf0 ‖ slot)    d = first 8 bytes of HKDF(viewRoot, "out-d" ‖ nf0 ‖ slot)
// Key of ciphertext 1:
k1  = HKDF(viewRoot, "ct1" ‖ nf0 ‖ C1 ‖ C2 ‖ C3, 32 bytes)

// Address a payer needs: ownerPk (32 bytes) followed by the recipient's X-Wing public key (1,216 bytes).
  • accrued is reward already earned and not yet turned into tokens. It travels with the note. index is the value of g the note was created against.
  • A wallet is rebuilt from its seed and the chain. This is a rule for the wallet, not a suggestion. It finds its deposits by trying counters against Deposited events and stops after 20 counters in a row with no match. It finds its own spends by trying k1 on every Spent event, and payments to it by trying its X-Wing key on ciphertext 0. Values come from the ciphertexts and the index from gRef in the event. Someone else may copy an ownerCommit into a deposit of their own, so several deposits can carry one ownerCommit.
  • Empty inputs are filled with fresh random numbers every time: rho, leafIndex and slot. They are never derived from the seed, because a repeated dummy nullifier would make a restored wallet's spend fail.
  • A view-only wallet holds viewRoot, spk and nk. It sees every note, computes every nullifier and cannot spend.
  • Addresses of one wallet can be linked. Each carries the same encryption key, so two people who compare addresses can tell they belong to one wallet. The diversifier keeps notes apart on-chain and does nothing for addresses. A user who wants separate identities uses separate seeds.
  • The short address is ownerPk and keccak256(key). It works only after the key has been published with Pool.announce, which is an ordinary transaction from a public account. Anyone who is given the short address can then tie the wallet to that account. The wallet uses the long address unless the user chooses otherwise.
  • Ciphertext 0, 1,216 bytes, is for the recipient of output 0: HPKE base mode with the X-Wing hybrid of X25519 and ML-KEM-768 as the key encapsulation (identifier 0x647A, 1,120 bytes), HKDF-SHA256 and ChaCha20-Poly1305, with the info string "murmuration/v1/ct0" followed by the chain id and the pool's address. Then an 80-byte payload and a 16-byte tag. The payload is asset (1 byte), value (12), accrued (12), rho (31), diversifier (8) and a memo (16). X-Wing is an IETF draft, not yet an RFC. The build pins draft 11 of 23 September 2026 and its test vectors.
  • Ciphertext 1, 96 bytes, is the sender's own record under k1 with ChaCha20-Poly1305 and a zero nonce: the value and accrued of output 1 (12 and 12), the value and accrued of output 2 (12 and 12), the claim in output 3 (12), and 20 spare bytes, with a 16-byte tag. The key depends on the three commitments, so a second attempt with a different fee or amount is sealed under a different key.
  • The pool checks the two lengths and nothing else about the ciphertexts. Every spend publishes exactly 1,312 bytes. A sender who posts garbage loses the payment for the recipient and gains nothing. This is the same in every shielded pool.
  • Not post-quantum: the Groth16 proof. Ownership and nullifiers rest on hashes only.

The circuit

There is one circuit, Spend. It takes two notes of one asset and a third note that pays the relayer, all with one owner. The third note can be of any listed asset, and that asset is public. The circuit produces two notes of the first asset, the change from the fee note, one note of the reward token, and an optional public amount. A private transfer has a public amount of zero. A withdrawal has a standard size as its public amount. A deposit needs no proof. Estimated size is about 32,000 constraints, to be measured by the build job, as is proving time on a mid-range phone.

The wallet pays the relayer in ETH when it holds an ETH note, because that says nothing about what was moved. A wallet with no ETH note pays in an asset it does hold, and then that asset is visible. When the fee asset and the spend's asset are the same, value can pass between the two sides, so a wallet with a single note can still pay a relayer and get change.

An input is empty when its value and accrued are both zero, tested as the one number value + 2^96 × accrued. The same test defines an empty output.

Constraints

  1. Keys. spk = H2(TAG_SPK, sk) and nk = H2(TAG_NK, sk).
  2. Assets. asset is one of the ids 1 to 5. feeAsset is one of 0 to 5. weight and weightFee are their constants from the table, with 0 for id 0. hasFee is 1 when feeAsset is not zero and 0 otherwise. same is 1 when asset equals feeAsset and 0 otherwise.
  3. Ranges. Every value, accrued, claim, earned, publicAmount and relayFee fits in 96 bits. gRef and each input's index fit in 90 bits. The division remainder in constraint 9 fits in 64 bits. Each leafIndex is given as 32 bits and each slot as 2 bits, and those same bits are the selectors used in constraint 5.
  4. Input notes. For each input, ownerPk = H4(TAG_PK, spk, nk, d), ownerCommit = H3(TAG_OC, ownerPk, rho), and commitment = H3(packed, index, ownerCommit), where packed uses asset for inputs 0 and 1 and feeAsset for input 2.
  5. Membership. For each input, the commitment placed at slot among others hashes with H4 to a leaf, and that leaf, with the bits of leafIndex choosing left or right at each of the 32 levels of path, hashes to root. The equality with root is enforced unless the input is empty.
  6. Nullifiers. nf[i] = H4(TAG_NF, nk, 4 × leafIndex + slot, rho) for inputs 0 and 1, from the same leafIndex, slot and rho used above, whether or not the input is empty. nf[2] is the same formula for input 2 when hasFee is 1, and 0 when hasFee is 0.
  7. Distinct inputs. Any two inputs that are both non-empty have different positions.
  8. Index order. For each input, gRef − index fits in 90 bits, so it is not negative.
  9. Reward earned. weight × (value₀ × (gRef − index₀) + value₁ × (gRef − index₁)) + weightFee × value₂ × (gRef − index₂) = earned × 2^64 + remainder.
  10. Outputs. C[k] = H3(packed(asset, valueₖ, accruedₖ), gRef, ownerCommitₖ) for k in 0 and 1, and C[2] = H3(packed(feeAsset, value₂′, accrued₂′), gRef, ownerCommit₂).
  11. Reward note. C[3] = H3(packed(TOKEN, claim, 0), gRef, ownerCommit₃).
  12. Value is conserved. Let t be input values 0 and 1 less output values 0 and 1 less publicAmount, and u be input value 2 less output value 2 less relayFee. Then t + u = 0 and (1 − same) × t = 0. Each side balances by itself unless both sides are the same asset, and then only the total has to balance.
  13. Reward is conserved. The three input accrued amounts plus earned equal the three output accrued amounts plus claim.
  14. The public asset is the real one. publicAmount × (asset − publicAsset) = 0.
  15. No fee, no fee note. When hasFee is 0, input 2 and output 2 are empty. Constraint 12 then makes relayFee zero.
  16. Binding. extHash takes part in one constraint so that no tool can drop it from the proof.

What the circuit leaves to the contract: that the root is recent, that the nullifiers are new and pairwise different, that gRef is a real checkpoint, that the public amount is a standard size the asset can pay, that the relay fee is under its ceiling, that the zero conventions in the table hold, and that extHash and the ciphertext lengths match the call.

What must be shown, and how

Revision 4.2 put everything under "machine-checked proofs". The review showed that some of its statements are not properties of a circuit at all, and that a circuit which accepts nothing satisfied every one of them. The list is now in four parts, and each part says how it is checked.

A. Machine-checked on the constraint system that goes into the ceremony. The relation theorem: every assignment that satisfies the constraints satisfies the sixteen constraints above as written in the formal specification, over the integers where they speak of sums. Then eleven lemmas about that relation, each published in plain words beside the formal statement.

  1. Spend authority. Each non-empty input's ownerPk is built from the spk and nk derived from the one sk in the witness.
  2. Membership. Each non-empty input, in the sense defined above, is a note in the tree under root at the position the proof uses.
  3. One nullifier per note. A nullifier is a function of the note's position, of the rho inside its ownerCommit and of the nk inside its ownerPk, and of nothing else. Two satisfying assignments that spend the same position publish the same nullifier. A non-empty input always publishes its nullifier.
  4. No value is created, per asset. Inputs 0 and 1 and outputs 0 and 1 carry asset. Input 2 and output 2 carry feeAsset. No position is used twice in one proof. The sums balance over the integers with the public amount and the relay fee, each side by itself, or together when the two assets are equal.
  5. No reward is created. Reward leaving equals reward entering plus earned. earned uses each input's committed index and the weight of that input's own asset. Output 3 is a token note with no accrued reward.
  6. Outputs start at the checkpoint. Every output's index is gRef.
  7. The public asset is true whenever a public amount is non-zero.
  8. Nothing is left free. Given the private inputs, feeAsset and gRef, the values nf[0..2], C[0..3], publicAmount and relayFee are determined. root is determined when at least one input is non-empty. publicAsset is determined when publicAmount is non-zero. extHash and gRef are free in the circuit and are fixed by the contract. Every intermediate signal is determined by the inputs.
  9. No wrap-around. No sum, product or difference reaches the field modulus in constraints 8, 9, 12 and 13, in the packed word, in the emptiness test or in the position.
  10. Every public input counts. Each of the 14 occurs in a constraint that survives compilation, and their columns in the constraint system are linearly independent, so the key holds a separate point for each one and a proof made for one set of public inputs does not verify for another.
  11. Honest spends are accepted. For every state the pool can reach, with values, indexes and checkpoints anywhere in the ranges the parameter table allows, the honest witness satisfies the constraints. This covers every kind of spend in the canary list and the ends of every range. Without it, a constraint that is one bit too tight would lock notes for good and every other lemma would still hold.

B. Checked on the verification key and the deployed verifier. These are facts about the ceremony's output and cannot be read off the circuit. The 15 input points of the key are pairwise different and none is the point at infinity. Every point is on its curve and the G2 points are in the right subgroup. Alpha, beta, gamma and delta are not the point at infinity, gamma and delta differ, and delta is not the generator. The key is recomputed from the final ceremony file by a second tool, and the chain of contributions is verified from the first file to the last. On the deployed verifier, changing any one public input of a valid proof makes it fail.

C. Assumed, named, and not machine-checked. That Groth16 proofs can only be made by someone who knows a satisfying assignment, which rests on the ceremony having had at least one honest contributor. That nobody can find two inputs with the same Poseidon hash, or an input for a given hash. Each appears in the formal statements as a written hypothesis and never as a hidden axiom.

D. Properties of the Pool contract, covered by tests, fuzzing and the audits. No nullifier is accepted twice and the three in one call are pairwise different. g stays under its bound for every sequence of calls. For each asset the values of all unspent notes add up to at most shielded, which is what keeps earned inside 96 bits.
