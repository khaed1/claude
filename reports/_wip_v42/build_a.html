Build specification

This section is what a build job works from. It replaces the design table of the first version 4 wherever the two differ. The review gives the reason for each difference, and the independent review gives the reason for what changed between revisions 4.1 and 4.2. Values marked param come from the parameter table and are frozen before the trusted-setup ceremony. Names are working names. Where this section does not say what to do, a builder stops and asks.

Conventions

ItemDefinition
FieldThe BN254 scalar field. Every hashed value is less than its modulus p, and the contracts reject inputs that are not
HashPoseidon with circomlib's parameters. H2, H3 and H4 take two, three and four inputs. On-chain they are the three poseidon-solidity contracts already deployed on mainnet, pinned by code hash and checked against the circuit with shared test vectors
Domain tagsEvery hash that is not a tree node or a leaf bundle takes a tag as its first input: TAG_SPK = 1, TAG_NK = 2, TAG_PK = 3, TAG_OC = 4, TAG_NF = 5. A note's packed word carries TAG_NOTE = 6 above bit 200, so it can never equal a small tag
AmountsUnsigned, at most 96 bits, in the asset's base units. The token's supply times 1018 must stay under 296, which allows up to about 79 billion tokens
Asset id8 bits, starting at 1. Zero means "no asset". The list and each asset's weight are constants in the circuit and the pool param
Reward indexOne number g for the whole pool, at most 90 bits, fixed-point with 64 fractional bits. It only grows
TreeAppend-only, depth 32, nodes H2(left, right). The empty leaf is ZERO = keccak256("murmuration.zero") mod p and empty subtrees are built from it. One leaf per transaction: leaf = H4(C0, C1, C2, C3), a bundle of four note commitments. An unused slot in a bundle holds the field element 0, which is no note's commitment
Positionpos = 4 × leafIndex + slot, where slot is 0 to 3. It identifies one note for good
TimeEvery schedule is measured in seconds of block time, never in block counts, so a change in Ethereum's slot time cannot shorten it. A screening epoch is one day. A reward checkpoint window is one hour. A cap step is 90 days. All count from GENESIS, a timestamp fixed in the final build param. Block counts elsewhere on this page are the equivalent at 12-second slots
Token transfersThrough a wrapper that accepts tokens returning no value, as USDT does. ETH is sent with call, never transfer

Keys, notes and addresses

// Keys. sk never leaves the wallet.
spk      = H2(TAG_SPK, sk)                 // proves the right to spend
nk       = H2(TAG_NK,  sk)                 // computes nullifiers; safe to give to a view-only wallet
ownerPk  = H4(TAG_PK, spk, nk, d)          // d: a diversifier, so one wallet can hand out many unlinkable addresses

// A note is (asset, value, accrued, index, ownerPk, rho).
ownerCommit = H3(TAG_OC, ownerPk, rho)     // hides the owner; this is all a deposit reveals about its recipient
packed      = TAG_NOTE·2^200 + accrued·2^104 + value·2^8 + asset
commitment  = H3(packed, index, ownerCommit)
nullifier   = H4(TAG_NF, nk, pos, rho)     // one per note position; published when the note is spent

// Address a payer needs: ownerPk (32 bytes) and the recipient's X-Wing public key (1,216 bytes).
// Short form: ownerPk and keccak256(key). The key is announced once through Pool.announce and read from the public snapshots.
  • accrued is reward already earned and not yet turned into tokens. It travels with the note. index is the value of g the note was created against.
  • Everything a wallet needs can be rebuilt from its seed and the chain. This is a rule for the wallet, not a suggestion. rho and d for a deposit come from a keyed hash of the seed and a per-wallet deposit counter, so a restored wallet finds its deposits by trying counters against Deposited events. rho for outputs 1, 2 and 3 of a spend comes from a keyed hash of the seed, the spend's first nullifier and the slot. Values come from the ciphertexts below and gRef from the Spent event.
  • Ciphertext 0, 1,216 bytes, is for the recipient of output 0: HPKE base mode over the X-Wing hybrid of X25519 and ML-KEM-768 (1,120 bytes of key encapsulation), then an 80-byte payload and a 16-byte tag. The payload is asset (1 byte), value (12), accrued (12), rho (31), diversifier (8) and a memo (16). X-Wing is an IETF draft, not yet an RFC. The build pins draft 11 of 23 September 2026 and its test vectors, with HPKE identifier 0x647A.
  • Ciphertext 1, 96 bytes, is the sender's own record, sealed with a key from the seed and the first nullifier: the value and accrued of output 1 (12 and 12), the value and accrued of output 2 (12 and 12), the claim in output 3 (12), and 20 spare bytes, with a 16-byte tag. Every spend publishes the same 1,312 bytes whatever it does.
  • The pool does not check ciphertexts. A sender who posts garbage loses the payment for the recipient and gains nothing. This is the same in every shielded pool.
  • Not post-quantum: the Groth16 proof. Ownership and nullifiers rest on hashes only.

The circuit

There is one circuit, Spend. It takes two notes of one asset and, when a relayer is paid, a third note of ETH, all with one owner. It produces two notes of the asset, the ETH change from the relay fee, one note of the reward token, and an optional public amount. A private transfer has a public amount of zero. A withdrawal has a standard size as its public amount. A deposit needs no proof. Estimated size is about 31,000 constraints, to be measured by the build job, as is proving time on a mid-range phone.

Constraints

  1. Keys. spk = H2(TAG_SPK, sk) and nk = H2(TAG_NK, sk).
  2. Asset. asset is one of the listed ids, never zero, and weight is that asset's constant from the table. weightEth is ETH's constant. The reward token's weight is zero.
  3. Ranges. Every value, accrued, claim, earned, publicAmount and relayFee fits in 96 bits. gRef and each input's index fit in 90 bits. The division remainder in constraint 8 fits in 64 bits. Each leafIndex is given as 32 bits and each slot as 2 bits, and those same bits are the selectors used in constraint 5.
  4. Input notes. For each input, ownerPk = H4(TAG_PK, spk, nk, d), ownerCommit = H3(TAG_OC, ownerPk, rho), and commitment = H3(packed, index, ownerCommit), where packed uses asset for inputs 0 and 1 and the ETH id for input 2.
  5. Membership. For each input, the commitment placed at slot among others hashes with H4 to a leaf, and that leaf, with the bits of leafIndex choosing left or right at each of the 32 levels of path, hashes to root. The equality with root is enforced unless the input's value and accrued are both zero, tested as one number value + 2^96 × accrued.
  6. Nullifiers. nf[i] = H4(TAG_NF, nk, 4 × leafIndex + slot, rho) for inputs 0 and 1, from the same leafIndex, slot and rho used above. For input 2 the same formula holds when its value or accrued is non-zero, and nf[2] = 0 when both are zero.
  7. Index order. gRef − index is between 0 and 290 for each input.
  8. Reward earned. weight × (value₀ × (gRef − index₀) + value₁ × (gRef − index₁)) + weightEth × value₂ × (gRef − index₂) = earned × 2^64 + remainder.
  9. Outputs. C[k] = H3(packed(asset, valueₖ, accruedₖ), gRef, ownerCommitₖ) for k in 0 and 1, and C[2] = H3(packed(ETH, value₂′, accrued₂′), gRef, ownerCommit₂).
  10. Reward note. C[3] = H3(packed(TOKEN, claim, 0), gRef, ownerCommit₃).
  11. Value is conserved. Input values 0 and 1 add up to output values 0 and 1 plus publicAmount. Input value 2 equals output value 2 plus relayFee.
  12. Reward is conserved. The three input accrued amounts plus earned equal the three output accrued amounts plus claim.
  13. The public asset is the real one. publicAmount × (asset − publicAsset) = 0.
  14. Binding. extHash takes part in one constraint so that no tool can drop it from the proof.

What the circuit leaves to the contract: that the root is recent, that the nullifiers are new and distinct, that gRef is a real checkpoint, that the public amount is a standard size the asset can pay, that the zero conventions in the table hold, and that extHash matches the call.

What the proofs must show

The launch gate requires the top statement and each lemma to be machine-checked against the constraint system that goes into the ceremony, with each statement published in plain words beside the formal one. Version 4.1 listed five properties. The independent review showed that a circuit missing whole constraints could satisfy all five, so the list is now a statement of the full relation with ten lemmas.

Top statement. For every proof the verifier accepts, there exist a key sk and up to three notes such that every constraint above holds: the notes are in the tree under root or are empty, they belong to sk, and the public inputs are exactly the specified functions of them.

  1. Spend authority. Each non-empty input's owner is derived from the sk the prover knows. Knowing nk and spk is not enough.
  2. Membership. Each non-empty input is a note in the tree under root, at the position the proof uses.
  3. One nullifier per note. The position inside each nullifier is the position proved in the tree, so a note has exactly one nullifier and a nullifier names one position.
  4. No value is created, per asset. Outputs 0 and 1 carry the inputs' asset, output 2 carries ETH, and the sums balance over the integers with the public amount and the relay fee.
  5. No reward is created. Reward leaving equals reward entering plus earned, earned uses each input's committed index and the weight of its own asset, and output 3 is a token note with no accrued reward.
  6. Outputs start at the checkpoint. Every output's index is gRef.
  7. The public asset is true whenever a public amount is non-zero.
  8. Nothing is left free. Given the private inputs, every public output is determined.
  9. No wrap-around. No sum or product in constraints 8, 11 and 12 can reach the field modulus.
  10. Non-malleability. Changing any one of the 13 public inputs of an accepted proof makes it rejected.
